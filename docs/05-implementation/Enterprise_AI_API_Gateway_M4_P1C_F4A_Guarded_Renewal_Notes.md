# M4-P1C-F4A guarded renewal backend

This backend implements the additive interface in the [R2 companion](../04-api/Enterprise_AI_API_Gateway_M4-P1C-R2_Guarded_Renewal_Dispatch_Boundary_Contract.md). M4 request lifecycle adoption belongs to F4B.

`RedisConcurrencySemaphore`, `LocalConcurrencyStore` and `RecoveryConcurrencySemaphore` expose `renew_guarded(policies, handle_or_lease_id, *, guard)`. The caller supplies synchronous `monotonic()` and `permit(sampled_at)` methods. Outcomes and attempt snapshots are immutable. The executing task retains `guarded_renewal_operation`, including phase, attempt snapshots and cancellation evidence, so the future lifecycle owner can observe cancelled operations. The caller retains earlier outcomes across invocations.

The Redis runtime lazily owns one separate guarded pool with an internal maximum of 16 connections and no command retransmission. It copies the issuing client's connection options and uses the existing finite Redis operation bound. Guarded script preparation uses this pool through the existing semaphore cache/lock, with an optional transport parameter on the loader. Legacy loading retains its existing client. This extension prevents queued guarded script preparation from reopening the legacy pool after runtime closure. Each EVALSHA reaches its own synchronous guard inside the final write coroutine. NOSCRIPT alone permits one reload/retry. Unsafe reply alignment disconnects the connection before pool return.

The guarded transport belongs to its constructing event loop. Execution, pool checkout, connection preparation and close enforce that owner. Close latches irreversibly before awaiting disposal. The final writer segment checks that latch synchronously before authorization, so closure and writer invocation linearize on the owning loop. A completed earlier write retains its evidence. A late connection establishment is immediately disconnected, and queued checkout cannot allocate another connection after closure.

Concurrent/repeated close calls share one retained disposal task. Cancelling a close caller stops that caller's wait while the transport retains and observes disposal. Existing R1 ownership and cutoff remain responsible for bounded shutdown waiting. This repair adds no cleanup duration or retry. The same runtime owner closes both guarded and legacy resources.

F2 makes runtime closure truthful: one runtime-owned disposal task attempts guarded and legacy cleanup and retains a sanitized `RedisDisposalError` naming each failed/unconfirmed obligation. A successful return confirms both obligations. Failure never becomes success on a repeated call, and guarded failure cannot skip legacy cleanup. The existing supervisor retains Redis as unclosed when this typed failure propagates and continues independent resource closure. Caller cancellation and the R1 cutoff stop waiting without cancelling the retained disposal task or claiming completion. The transport close latch is set synchronously before scheduling disposal; no post-close renewal write is authorized. No retry or new deadline is introduced.

F3 supplies the existing supervisor-owned `LifecycleScope` through the lifespan Redis close wrapper. Runtime closure retains that live authority without calculating another deadline. Each disposal stage checks latched expiry immediately before entry, and the guarded disposal task checks again at its actual first execution after scheduling. The close latch itself remains synchronous even when disposal cannot start. Expiry blocks an unstarted stage permanently; a later close cannot restart it. Per-resource accounting distinguishes not-attempted, pending, completed and failed stages. Pending work at cutoff remains retained/observed, and its eventual result never authorizes a subsequent stage after cutoff. An omitted stage remains a sanitized error/unclosed obligation. Ordinary unmanaged `close()` retains its existing behavior without requiring G. Supervisor code and frozen contracts are unchanged.

F4 adds an instance-local, redis-py 8.1.0-pinned `ManagedPoolDisposal` adapter for managed shutdown only. It preserves the installed pool's available/in-use enumeration and actual gather scheduling, wrapping captured connection disconnect methods so each child checks the same live authority at actual coroutine entry. It also fences pool disconnect and the legacy pool close hook after preceding awaits. No global asyncio/redis-py patch is installed. The adapter retains connection objects, fixed numeric accounting slots and started tasks; states distinguish not-attempted, pending, completed, failed, skipped and unresolved. Any omitted or unconfirmed connection keeps the pool and runtime unresolved. Repeated entry cannot retry an omitted/failed connection or duplicate a completed disposal.

The installed connection disconnect closes its writer before waiting for its existing close waiter; it creates no further connection-disposal task. Its socket timeout and R1 owner bound their respective waits. Maintenance shutdown cancels/joins already-existing tasks; subsequent pool entry is fenced again. Because redis-py can swallow a writer-close `OSError`, a returned disconnect is accepted as confirmed only when any captured writer's protocol close waiter has completed successfully. Missing, pending, cancelled or failed confirmation remains unresolved. This is version-sensitive private-API integration. Ordinary unmanaged close paths retain their original methods. Deterministic tests exercise real pool gather scheduling with recording connections; disposable Redis tests separately confirm managed closure of real guarded and legacy sockets. These tests do not constitute platform process-shutdown acceptance.

F5 installs instance-local pool ownership observation at lazy client/pool creation, before the first connection can be admitted. Allocation registers each connection synchronously; checkout and connection establishment retain completion futures and their executing tasks until termination. Normal use delegates to the original methods, with no new retry or background task. Completed observations are compacted to a last-outcome slot per connection rather than retained as an unbounded operation history.

Managed runtime close validates the existing active process scope and synchronously fences both pools before its first disposal handoff. Pool allocation, available reuse, lock-waiting checkout, direct connect and reconnect all recheck that irreversible fence. Establishment already in progress remains owned; no usable connection is returned after closure. Disposal waits for its actual termination only within the same R1 cutoff, then closes the complete registered connection set. A late writer after cutoff remains explicitly unresolved; no compensating disconnect is started after expiry. Connections admitted outside the instrumented path cannot be silently treated as disposed. Uninstrumented work already in use when observation is installed fails managed closure conservatively.

Guarded establishment no longer races its own compensating disconnect against managed pool disposal. The managed owner resolves that obligation after establishment terminates. An error-path disconnect that already requested writer closure may join the existing close confirmation under the original socket bound and R1 authority, without issuing another disconnect. Shutdown rejection wrapped by redis-py is normalized to closed admission rather than a new availability failure. Unmanaged close retains its original path. All adapters are per-instance; no unrelated client, global redis-py method, supervisor, signal adapter, frozen contract or renewal algorithm is changed.

The same owner observes already-started disconnects, retains their writer confirmation, and avoids repeating confirmed disposal. Registered connections retired from the current pool collections remain part of the disposal set; eligible retired cleanup has its own final entry check. If managed authority is attached only after an unmanaged disposal has already started, admission is still fenced but that earlier operation is not retroactively certified: managed closure remains unresolved, with no retry. Process-scope validation occurs before mutating either pool. Real Redis 7.4.11 tests cover both pools' admission denial and guarded/legacy socket initialization during closure; controlled-clock tests separately cover expiry and late-writer accounting. Platform shutdown acceptance and F4B remain separate.

At the managed fence, each in-flight task receives one exception-observation callback; managed cleanup tasks receive the same observation on entry. A weak task set prevents repeated callback registration without retaining completed tasks indefinitely. Cancellation requests do not complete the tracked obligation until the underlying coroutine actually exits, including when it suppresses cancellation temporarily.

F6 retains writer-specific closure obligations independently of the connection's current writer pointer. Each record holds the writer, its protocol generation and that generation's original close-confirmation future. A writer-less disconnect records no new writer request and cannot remove older pending, failed, cancelled or unsupported confirmation evidence. Reconnection adds a distinct obligation; closing a newer writer cannot resolve an older one. Only successful completion of the captured original protocol future establishes confirmation. Confirmed records are compacted; unresolved records remain owned rather than being overwritten by the latest writer.

Managed connection and pool completion both check all outstanding writer obligations. Existing confirmation futures may be joined only within the original socket bound and process cutoff; late successful confirmation can be inspected synchronously without new cleanup or another waiter. A previously failed runtime close retains its terminal failure on repeated calls even when factual writer confirmation later becomes available. Runtime, supervisor, admission fencing, establishment tracking and unmanaged disconnect behavior are unchanged. Tests cover multiple writers and protocol replacement, failed/cancelled/invalid future completion, no-op repetition, and authoritative late confirmation. Real Redis tests inject a close failure on a real writer and separately use test-owned cleanup to complete its genuine close waiter; that cleanup is not claimed as production recovery behavior.

Each captured confirmation future receives one exception-observation callback, tracked weakly. Late error/cancellation is observed without creating cleanup work, a retry, or a new waiter. Confirmation follows the installed StreamReaderProtocol contract: the original future must finish normally with `None`; a cancelled, exceptional, unsupported or otherwise invalid completion remains unconfirmed.

Attempt validation keeps failure categories on definitive `RESOLVED_ERROR` evidence only, limited to the existing Redis dependency/non-dependency categories. `RESULT`, `NOSCRIPT` and `UNRESOLVED` cannot carry contradictory error classifications; operation-level failures remain separate. The committed R2 companion still labels itself draft/not frozen; this implementation follows the explicitly authorized F4A/F2 scope without changing that governance status.

The writer integration depends on redis-py 8.1.0 private connection fields. Other redis-py versions and connection classes, including TLS, fail closed for guarded renewal. Legacy client construction and renewal remain available through their existing paths. Real TLS acceptance is required before adding guarded TLS support.

The guarded local method checks eligibility under the existing lock before cleanup and samples local lease time there for permitted execution. Legacy local renewal retains its existing behavior. The facade routes using original handle provenance and retains existing dependency-unreachable and local-generation bookkeeping.

Unit tests cover deterministic writer/mutation gates, outcome history, error classification, cancellation, routing and runtime ownership. Disposable Redis acceptance is explicitly enabled with `RUN_M4_F4A_REDIS=1` for `tests/integration/test_guarded_renewal_runtime.py`. Its fixture owns a uniquely named/labeled Redis 7 container, dynamic loopback port, random disposable credentials and tmpfs data. Teardown checks the exact identity after every creation result, including timeout/interruption, verifies the ownership label and immutable ID, removes only that ID and confirms absence. Fake CLI tests cover uncertain creation, identity mismatches and cleanup failure. It never uses Gateway Redis.

Production M4 lifecycle/anchor integration, request/process cutoff adoption and release orchestration remain deferred to F4B. Existing R1/R8/R9 ownership rules continue to govern that work.


## F7 — operation-level cleanup cutoff

The lifecycle-to-facade-to-transport K16 probe reproduced a renewal sent at t=2 whose cancellation started disconnect at the existing process cutoff t=3. F7 propagates the existing LifecycleScope with an internal context manager around guarded invocation; the public `renew_guarded(..., guard=...)` signature and guard protocol are unchanged. Context propagation reaches redis-py's timed-send child tasks. GuardedRenewalOperation retains the same scope and any deferred connection obligations. No deadline, G, retry, fallback or lease semantics change.

Both explicit transport cleanup paths (SCRIPT LOAD and EVALSHA) check live authority at actual cleanup coroutine entry. Per-instance connection disconnect observation also checks that authority before invoking the original disconnect, covering inherited redis-py response/error/reconnect cleanup. Pool release checks at entry and prevents quarantined connections returning to the available set; a release lock handoff cannot bypass the connection disconnect gate. Already-started cleanup remains observed, not restarted or declared complete by cancellation.

Forbidden cleanup synchronously quarantines the connection: it retains its pool capacity slot, complete ownership registry entry and original writer/protocol confirmation. This prevents unsafe reuse without asserting physical closure. The first deferred scope remains attached so a later context cannot replace expired authority to retry cleanup. No deferred cleanup task or automatic retry is created. Managed runtime disposal must still satisfy original F6 confirmation requirements and retain unresolved resources. Genuine late confirmation may update factual accounting without another disconnect.

The lifecycle retains deferred-resource evidence even when cancellation occurred before any renewal attempt. This is separate from backend execution uncertainty and does not fabricate a result. Unmanaged calls without request authority retain existing cleanup behavior; no G is imposed on legacy M3 clients. All hooks remain instance-local.

F7 deterministic regressions cover preparation/drain/response/NOSCRIPT cancellation before, at and after cutoff; scheduled versus actual cleanup entry; work already started; pool-release lock handoff; quarantine/capacity accounting; original future identity; earliest request/process boundaries; irreversible deferred authority; and inherited read-response cleanup. Existing F4A/F6 and partial F4B tests remain regression gates. Six disposable Redis 7.4.11 variants exercise actual lifecycle/facade/transport/socket paths during initialization, drain and response, before and at process cutoff. Fixture-owned socket teardown is explicitly separate from production cleanup and is not platform shutdown certification. This repair makes no F4B completion claim.
