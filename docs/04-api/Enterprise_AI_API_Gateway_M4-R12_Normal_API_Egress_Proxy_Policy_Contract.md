# M4-R12 — Normal API Egress Proxy / Environment Proxy Policy Contract

Status: **FROZEN M4 V1 CONTRACT — DIRECT EGRESS ONLY.** Documentation-only reconciliation. This contract selects the outbound connection path needed to implement M4-R11; it does not implement that path or declare the whole M4 engine ready.

## 1. Authority and decision

[M4-R11](Enterprise_AI_API_Gateway_M4-R11_Normal_API_Outbound_Destination_SSRF_Contract.md) requires the approved canonical destination IP and port to be the destination actually connected to, with all selectable DNS answers checked and no independent post-validation resolution. It permits ordinary private/on-prem upstreams but denies the protected platform listeners and the frozen OpenAPI metadata addresses. [M4-R5](Enterprise_AI_API_Gateway_M4-R5_Upstream_HTTP_Client_Pool_Contract.md) freezes one process-local shared `httpx.AsyncClient` but deliberately leaves its proxy behavior unresolved. M4-R3's no-follow redirect rule and M4-R10's timeouts are unchanged.

**M4 V1 Normal API traffic uses direct outbound connections only.** It does not use environment-discovered proxies or an explicitly configured application egress proxy. There is no tenant, service, route, or deployment proxy selection field for this client in M4 V1. An operator needing an application egress proxy requires a later explicit contract and acceptance evidence before enabling one; M4-R12 does not authorize a proxy merely because it is deployment-owned. This is a narrow M4 V1 choice, not a ban on network-layer routing or proxies used by unrelated dependencies. Ordinary direct private/on-prem HTTP(S) upstreams remain eligible under M4-R11.

## 2. Environment isolation and HTTPX mapping

The shared Normal API client MUST effectively operate with `trust_env=False`, no `proxy=` value, and no proxy mounts for M4 V1. `HTTP_PROXY`, `HTTPS_PROXY`, `ALL_PROXY`, `NO_PROXY`, and their lowercase equivalents MUST NOT influence its upstream routing, including bypass selection. Other process clients and dependencies may have their own environment behavior. The Normal API client must not inherit an application-global proxy transport or mount that changes this rule. The existing `create_normal_api_upstream_client()` currently passes only `limits=`, so HTTPX 0.28.1 supplies `trust_env=True` by default; this is an implementation gap, not authorization to retain implicit proxying.

The locked HTTPX 0.28.1 implementation ties more than proxy discovery to `trust_env`: with `verify=True`, `trust_env=True` also consults `SSL_CERT_FILE` and `SSL_CERT_DIR`, while `trust_env=False` instead uses the library's normal certifi-backed default context. Thus these certificate environment variables MUST NOT be treated as Normal API custom-CA configuration merely by inheriting HTTPX environment behavior. `trust_env=False` does **not** disable certificate or hostname verification. Whether and how an operator supplies a custom CA/SSL context is a separate TLS-trust contract; that later policy must use an explicit, reviewed client configuration rather than silently restoring `trust_env=True`. HTTPX exposes `.netrc` authentication through explicit `NetRCAuth`; M4 V1 MUST NOT supply it for this shared client or acquire upstream credentials from a user's home directory or environment proxy credentials. This paragraph records the necessary environment-isolation consequences, not a general TLS trust-store or upstream-credential design.

## 3. M4-R11 validation-to-connection boundary

With no application proxy, the ultimate service upstream and the outbound TCP peer are the same connection target. For each **new** connection, the M4-R11 resolver/connector MUST assess every candidate address, deny a mixed protected/allowed set, and bind the selected approved `(canonical IP, destination port)` to the actual connect operation. The original service hostname remains the HTTP Host and HTTPS certificate-name identity. Resolving/checking first and then passing the hostname to a separately resolving HTTPX transport is not sufficient. An existing pooled connection may be reused only under M4-R11's current-inventory and trustworthy-peer-identity rule. If the available transport cannot uphold those invariants, Normal API outbound execution remains blocked; `trust_env=False` alone is not an SSRF defense.

An external network-layer proxy, service mesh, or transparent interception outside this application's HTTPX configuration does not count as an M4 application egress proxy. Deployment owners MUST still ensure that such infrastructure cannot redirect an approved direct connection to a protected or metadata endpoint or defeat the peer-binding guarantee. Where that cannot be established, Normal API execution is not ready. M4-R12 does not claim that a process can inspect an opaque intermediary's ultimate destination.

If a future contract permits an explicit application proxy, it must separately define the proxy's deployment-owned identity, authentication, TLS trust, CONNECT/absolute-form behavior, DNS ownership, ultimate-destination enforcement, and validation-to-connect binding for **both** the proxy peer and the upstream target. A proxy being reachable or trusted does not itself make an arbitrary target safe. No tenant or service administrator may bypass M4-R11 by selecting a proxy. This future possibility is not an M4 V1 feature.

## 4. Failure and lifecycle compatibility

An implicit environment proxy must never be attempted or used as a fallback when direct connection fails. Invalid/unexpected proxy configuration affecting the Normal API client is a startup/configuration error; it must not silently become an alternate route. M4-R11 destination or peer-binding denial remains deterministic local preparation **before** circuit admission: the existing safe `500 gateway_internal_error` response applies before downstream commitment, with no upstream I/O or circuit completion; consumed rate admission is not refunded, and an acquired concurrency handle receives its one provenance-aware terminal release attempt. This contract adds no proxy-specific public error code. A direct upstream transport failure **after** successful security validation and circuit admission remains governed by M4-R2, M4-R9, and M4-R10, not reclassified as an SSRF denial.

The M4-R5 client ownership and pool limits, M4-R3 redirect behavior (`follow_redirects=False`; forward `Location` unchanged), and M4-R10 per-request timeout policy remain unchanged. No proxy path, retry, redirect-follow, fallback, or second upstream attempt is introduced.

## 5. Persistence, OpenAPI, and acceptance

This decision adds no database field or table, migration, tenant configuration version, M3-R3A current-state consumer, Admin API field, or static/generated OpenAPI change. The frozen OpenAPI egress-security requirements remain binding. No proxy URL, credentials, destination, DNS answer, or raw exception text may be logged; safe bounded reason categories and request correlation remain subject to existing telemetry rules.

Required later acceptance evidence includes: (1) uppercase and lowercase HTTP(S)/ALL proxy variables do not change the Normal API TCP peer; (2) uppercase and lowercase NO_PROXY do not change routing; (3) unrelated application clients may retain their own environment behavior; (4) no explicit proxy, proxy mount, or netrc auth is attached to the shared Normal API client; (5) `trust_env=False` does not disable HTTPS certificate/hostname verification; (6) `SSL_CERT_FILE`/`SSL_CERT_DIR` are not accidentally presented as supported Normal API custom-CA settings; (7) approved direct private/on-prem upstreams remain reachable; (8) protected/metadata targets are denied before circuit admission with no upstream I/O; (9) validation and the actual direct peer are bound across DNS changes, including pooled-connection checks; (10) direct transport errors do not trigger a proxy fallback; and (11) M4-R5 pool lifecycle, M4-R3 redirects, and M4-R10 timeouts retain their existing behavior. Use controlled local listeners and resolver/connector fakes, not internet endpoints or a preflight-only DNS mock, for the peer-binding proof.

## 6. Narrow supersession

M4-R12 resolves only the M4-R5/M4-R11 question of Normal API application-proxy ownership and HTTPX environment discovery for M4 V1. It does not change M4-R11 destination policy, choose a custom CA or broader TLS policy, change upstream credential injection, alter redirects/timeouts, or add a service/tenant proxy control. M4 outbound implementation still needs a connector that actually satisfies M4-R11's validation-to-connect invariant.
