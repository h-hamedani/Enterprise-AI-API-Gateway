# M4-R18 — Normal API Service/Route Current-State Consumer Contract

Status: **FROZEN M4 V1 CONTRACT — DOCUMENTATION ONLY.** This contract fixes the Normal API runtime configuration read model. It does not implement a consumer, cache, API, schema, or migration.

## 1. Authority and one runtime truth path

[M3-R3A](Enterprise_AI_API_Gateway_M3-R3A_Configuration_Consumer_Reconciliation_Completeness_Contract.md) separates monotonic observed version from process-local reconciliation completeness; every required consumer must reconcile authoritative tenant current state, including after a missed event or equal-version pending initialization. [M4-R6](Enterprise_AI_API_Gateway_M4-R6_Normal_API_Request_Body_Limit_Contract.md) and [M4-R10](Enterprise_AI_API_Gateway_M4-R10_Normal_API_Upstream_Timeout_Policy_Contract.md) already require one Normal API service/route current-state consumer, not separate body-limit or timeout consumers. Existing PostgreSQL `normal_api_services`, `normal_api_routes`, and `service_credentials` remain authoritative persisted configuration. Admin mutations commit audit and configuration version with the business change and publish invalidation post-commit; publication itself is not durable truth.

M4 V1 uses **one process-local Normal API service/route current-state projection per OS process** as its request-execution configuration authority. For each locally known tenant it participates as **one required M3-R3A current-state consumer** with a `reconcile_current_state(tenant_id)` capability loading authoritative PostgreSQL current state. It covers both service and route resources in one coherent tenant projection/generation. New requests do not read service/route configuration directly from PostgreSQL as an alternative execution path, and there is no Redis configuration projection or stale-cache fallback. PostgreSQL is read for authoritative consumer reconciliation, not as a per-request bypass of an unusable projection. M3 rate, concurrency, circuit, and other mutable traffic state remain in their existing owners, never copied into this configuration projection.

The current `InvalidationRegistry.register_required_consumer()` API is keyed to one `(tenant_id, resource_type, resource_id)` event callback. It does **not yet** provide a tenant-wide required-consumer registration covering both SERVICE and ROUTE events with one membership identity. Runtime implementation must supply that capability consistently with M3-R3A (or an equivalent adapter with one required consumer and correct event invalidation), **without fabricated resource IDs, synthesized missed events, or event-history replay**. The present API shape is an implementation prerequisite, not authorization to register fake per-resource consumers or claim completeness from a non-required tenant callback. This document does not change registry code.

## 2. Projection content and coherent admission

The authoritative tenant projection must include existing execution-relevant service fields: ID, tenant ownership, slug, ACTIVE/disabled status, `upstream_base_url`, `request_body_limit_bytes`, and connect, pool, write, read-idle, and pre-response timeout values. It must include existing route ID, tenant/service association, ACTIVE/disabled status, method, `path_pattern`, `priority`, nullable `timeout_ms`, `header_policy`, and `upstream_path_template` as persisted metadata (the template remains inactive in M4 V1 under M4-R1). It must include the active service-credential **identity/configuration metadata** needed to select `NONE`, `STATIC_BEARER`, or `STATIC_HEADER` and its key version/header name where applicable. No tenant/service CA or TLS override field exists or is invented; M4-R13's CA setting and other deployment settings remain process startup configuration outside M3-R3A. API-key permissions and rate-policy values must still be resolved by their own authorized/runtime owners; this projection is not a substitute for authentication or protection policy checks.

Do not put decrypted secrets, raw credential material, or raw ciphertext in an ordinary diagnostic/config snapshot. At outbound construction, select and decrypt only the **exact credential identity captured in the request's coherent configuration snapshot**, using the established tenant/service-safe secret boundary. Never silently switch to a newer credential after snapshot capture or fall back to an absent/invalid credential. If that exact row cannot be safely loaded/decrypted, fail closed under the existing local-configuration error boundary before upstream I/O. A rotated older row retained for lifecycle purposes may serve an already admitted in-flight request whose snapshot captured it; new snapshots use the newly reconciled active identity. No cross-tenant credential reference is allowed.

For every **new** Normal API request, obtain the M3-R3A usability predicate and service/route values at one coherent generation boundary. A standalone `is_tenant_reconciled()` check followed by independently mutable service and route reads is forbidden. The admission operation must atomically establish that the tenant is registered, initialization is complete, reconciliation is not required, the fenced completeness certificate is still valid, and the service/route values belong to that same published generation. Locking, immutable copy-on-write, or equivalent fencing is an implementation choice; a changed/invalidated certificate during capture fails admission rather than returning mixed values. One request receives one immutable service+route execution snapshot and does not re-read mutable configuration mid-flight. No new persisted service, route, or tenant version field is required: process-local generation identity is an internal coherence token, **not** a second authoritative numeric configuration version.

M3-R3A's `is_tenant_reconciled(tenant_id)` is **point-in-time evidence**, not a guarantee that PostgreSQL cannot commit immediately afterward. A request that successfully captures generation G may finish on G even if an Admin change later creates G+1. If dirty/pending/invalidation becomes observable **before** capture finishes, the request fails closed. If it occurs **after** capture, that request may continue on its immutable snapshot; subsequent requests cannot capture stale G while the tenant is unusable. A newly accepted event, required callback failure, version gap, consumer registration/replacement, PostgreSQL lookup failure, or fence mismatch invalidates eligibility according to M3-R3A. Observed-version equality alone never reopens admission.

## 3. Reconciliation, lifecycle, and failure behavior

The consumer reconciles tenant-wide **current** service, route, and active-credential metadata from PostgreSQL into a coherent candidate generation. Publish it only after the required callbacks and M3-R3A's start/end PostgreSQL version fence certify a stable tenant state; a partial load, failed callback, changed end version, or DB failure leaves the tenant uncertified. A complete generation must remove or mark unusable missing/deleted/disabled resources and routes whose parent service is not ACTIVE. No stale executable route survives a delete/disable reconciliation. Service and route values are never mixed across generations (for example, new route with old base URL or old service with new header policy). Resource-specific event callbacks may invalidate or refresh as permitted by M3-R3A, but a later successful callback does not by itself clear `reconciliation_required` or pending initialization; only a successful tenant-wide current-state pass can certify the required consumer.

There is **no full-table tenant discovery scan** at startup. A tenant enters this process's M3-R3A reconciliation membership through the established local registration/lifecycle path when it becomes relevant to authorized execution; first contact may trigger an immediate fenced initialization attempt or wait for the managed reconciler, but it must not execute until complete. Empty membership remains valid and certifies no tenant. Each OS process has its own projection, registration, certificate, and reconciliation work. A restart begins uninitialized; Redis Pub/Sub loss, flush, callback failure, and equal-version pending initialization are repaired only through M3-R3A current-state reconciliation, not replay or guessing. M3 does not promise simultaneous cross-process visibility after a commit.

Successful Admin persistence, audit/config-version advancement, and post-commit publication do **not** imply immediate executability on every process. Service/route creation becomes executable on a process only after its coherent tenant state includes the new resource. Base URL, method/path, header policy, body limit, timeout, active credential reference, and ACTIVE/disabled changes affect later requests only after the process has a usable reconciled generation. When a process **knows** its tenant certificate is invalid/dirty/pending, it cannot serve a new request from its old projection, including after a delete/disable. After successful reconciliation, deleted or disabled services/routes are absent from executable resolution. An in-flight request already holding a coherent snapshot is not retroactively mutated; ordinary M4-R8/R9 request lifecycle still applies. This is an eventual per-process propagation model bounded by the existing M3 invalidation/reconciliation mechanisms, not an invented synchronous global read-your-write barrier or cross-replica coordinator.

An uninitialized, pending, dirty, incomplete, or otherwise known unusable tenant current state **fails closed for new Normal API execution**: return the existing safe **500 `gateway_internal_error`** before protection admission or upstream I/O. This is a Gateway configuration-consistency failure, not `upstream_unavailable`, circuit evidence, or permission to use direct PostgreSQL/stale-cache fallback. Do not expose version numbers, resource identities, topology, callback exceptions, or secret metadata in the public envelope. This temporary failure is distinct from a safely resolved unknown/disabled service or route; the public mapping for such a resolved resource belongs to the separate runtime endpoint/resolution contract, and M4-R18 does not invent it. An unexpected missing/invalid value inside a supposedly certified generation is an internal consistency fault and also fails closed rather than manufacturing a route or default.

## 4. Compatibility, privacy, and acceptance

The existing tenant-aware relational keys, service/route columns, service-credential lifecycle, Admin audit/config-version transactions, and M3-R3A process-local version/certificate state suffice. M4-R18 adds **no database migration, tombstone/event table, persisted version field, service/route schema field, runtime setting, Admin/public OpenAPI field, or new error code**. It requires a later runtime registration/consumer implementation, but not a new M3-R3A version store. Keep only bounded version/generation/result categories in operational diagnostics; never log raw base URLs, tenant/service/route IDs as metric labels, credential material/ciphertext, header values, query/body content, or uncontrolled exceptions. Request telemetry may carry only identifiers already authorized by its persisted schema. Runtime protection counters and leases do not enter the configuration snapshot.

Acceptance must prove: (1) complete initialization in one process; (2) pending/partial initialization fails closed; (3) create service and route then execute only after reconciliation; (4) base URL change affects a later snapshot; (5) route method/path change does likewise; (6) header policy change; (7) body limit change; (8) timeout change; (9–10) disabled service/route blocks new snapshots; (11–12) deleted route/service is not retained as executable, where a deletion path exists; (13) an in-flight request continues on captured G; (14) later request sees G+1 only after usable reconciliation; (15) missed event/version gap repairs from current state; (16) restart initializes afresh; (17) dirty/pending fails closed with no DB fallback; (18) equal PostgreSQL/local version still initializes pending consumer; (19) multiple OS processes reconcile independently; (20) a deleted resource cannot survive a successful candidate-generation swap; (21) security-sensitive update cannot be bypassed by known-stale state; (22) no secret in projection diagnostics; (23) no circuit/concurrency runtime state in projection; (24) no migration/new version column; (25) certificate invalidation racing snapshot capture is fenced; (26) service/route cannot be mixed across generations; (27) credential rotation selects the captured exact identity and never silently changes it mid-request; (28) a failed callback followed by later successful event does not certify the tenant; (29) a changed/failed PostgreSQL end fence does not publish usable state. Use controlled race gates, real PostgreSQL and Redis integration where needed, and no fabricated resource event IDs or arbitrary sleeps as correctness proof.

## 5. Narrow supersession

M4-R18 resolves only M4's service/route runtime read and fail-closed boundary. It does not weaken M3-R3A's fenced completeness rules, create a second version store or runtime truth path, modify M3 traffic protection state, make Admin writes synchronously visible across processes, or replace M4-R1 through M4-R17 request/proxy semantics.
