# M4-R3 — Normal API Header Policy Contract

Status: M4 V1 contract reconciliation only. No runtime, Admin API, schema, test, migration, or OpenAPI implementation is part of this document.

## 1. Authority, scope, and precedence

The [M4 Normal API Engine Execution Pack V1.1](../05-implementation/Enterprise_AI_API_Gateway_M4_Normal_API_Engine_Execution_Pack_V1.1.docx) requires strict bidirectional header filtering, canonical `X-Request-ID`, removal of client Gateway Authorization, upstream credential injection after filtering, and pass-through of upstream `Location` without following redirects. The [API Specification V1.2.2 Final](Enterprise_AI_API_Gateway_API_Specification_V1.2.2_Final.docx), [OpenAPI 3.1 V1.2 Final](Enterprise_AI_API_Gateway_OpenAPI_3.1_V1.2_Final.yaml), [HLD V1.1 Corrected](../02-architecture/Enterprise_AI_API_Gateway_HLD_V1.1_Corrected.docx), and [PRD V1.4](../01-product/Enterprise_AI_API_Gateway_PRD_V1.4.docx) preserve the client/upstream authentication separation. The [Physical DB / Alembic Spec V1.2 Final](../03-data-model/Enterprise_AI_API_Gateway_Physical_DB_Alembic_Spec_V1.2_Final.docx) and current models provide nullable route JSONB `header_policy` and encrypted `service_credentials`, but no service header-policy column. The [M2.6 Registry Reconciliation](Enterprise_AI_API_Gateway_M2.6_Normal_API_Registry_Contract_Reconciliation.md) explicitly leaves JSON keys and runtime header behavior undefined. [M3-R13](Enterprise_AI_API_Gateway_M3-R13_Observability_Security_Boundary_Contract.md) governs operational redaction. [M4-R1](Enterprise_AI_API_Gateway_M4-R1_Normal_API_Routing_Path_Resolution_Contract.md) and [M4-R2](Enterprise_AI_API_Gateway_M4-R2_Normal_API_Circuit_Outcome_Classification_Contract.md) remain unchanged.

This contract supersedes only M2.6's *unspecified runtime meaning* for `route.header_policy` and qualifies the M4 pack's “route/service header policy” phrase: **M4 V1 policy is ROUTE-ONLY**. A service has no representable header-policy field; service credentials are a separate managed-auth configuration, not a service header policy. No service-level inheritance, merge, or hidden default object exists.

## 2. Exact route JSON shape and default

`header_policy` is either SQL/JSON `null` or exactly an object of this shape:

```json
{"request_allowlist":["accept","content-type","user-agent"]}
```

`request_allowlist` is the **only** permitted key. When the object is present, this key is required and its value is an array of unique, non-empty HTTP field names, canonicalized to lowercase ASCII. A field name must be a valid HTTP token; leading/trailing whitespace, controls, colon, and non-ASCII are invalid. Duplicate names after case folding, unknown JSON keys, wrong types, and `null` for the list are invalid. List order has no forwarding precedence. There is no request denylist, response allowlist/denylist, route static-header map, rewrite expression, secret reference, wildcard, or regex key in V1.

`header_policy = NULL` means the **safe platform default request allowlist** `accept`, `content-type`, and `user-agent`; `{}` is invalid, not another spelling of NULL. A non-null `request_allowlist` **replaces** the default list. An empty list forwards no caller-supplied application header. An absent key in a non-null object is invalid. Unknown caller header names are dropped unless explicitly listed and otherwise eligible. The policy affects only caller-to-upstream application headers; mandatory generated headers and managed upstream credentials are not caller headers.

The list is exact-name matching after lowercase comparison; it does not match prefixes or patterns. The Admin write path must reject an invalid policy before persistence. An already-persisted invalid policy fails closed at runtime: do not send an upstream request and return the existing safe `500 gateway_internal_error` configuration-failure envelope. Never silently ignore an unknown policy key or treat malformed JSON as unrestricted forwarding.

## 3. Request filtering and precedence

Process request headers in this order: (1) validate HTTP syntax/framing; (2) remove mandatory forbidden and hop-by-hop fields, including fields nominated by `Connection`; (3) select only caller fields in the effective route allowlist; (4) replace/generate Gateway-controlled fields; (5) inject the ACTIVE service credential, if any, after filtering. A route allowlist can never override steps 1, 2, 4, or 5. Header names are compared case-insensitively and emitted in standards-compliant form; case changes do not change identity.

Always remove caller `Authorization` (including `Bearer gw_...` and any other value), `Proxy-Authorization`, `Proxy-Authenticate`, `Host`, `Content-Length`, `Cookie`, `Forwarded`, every `X-Forwarded-*`, `X-Request-ID`, and every `X-Gateway-*` field. Never forward the Gateway key in another header. Also remove `Connection` and every field name it nominates; `Keep-Alive`, `TE`, `Trailer`, `Transfer-Encoding`, and `Upgrade` are unconditionally forbidden. They cannot be allowlisted. The HTTP client derives upstream `Host` from the validated resolved authority and derives framing/`Content-Length` from the actual outgoing body; caller values never select authority or framing. Invalid or ambiguous inbound framing, including conflicting duplicate `Content-Length` or `Content-Length` plus transfer-encoding where not safely normalized by the server stack, is rejected before forwarding.

`X-Request-ID` is overwritten with the Gateway-generated canonical UUID v7. A client-supplied request ID may be retained only as separate, validated non-canonical correlation metadata under the existing request-context contract; it is not forwarded as `X-Request-ID`. M4 V1 neither trusts, appends to, nor generates `Forwarded`/`X-Forwarded-*` headers for upstream. The existing `trusted_proxy_cidrs` used for Control Plane client-IP protection does not by itself authorize an outbound forwarding-chain policy.

Caller `Cookie` is unsupported and stripped; there is no browser-session pass-through. Caller `Authorization` is **never** an upstream application-auth channel. Gateway-managed `STATIC_BEARER` sets upstream `Authorization: Bearer <decrypted secret>`; `STATIC_HEADER` sets its validated configured header name/value; `NONE` injects neither. The active credential is loaded tenant/service-safely and decrypted only for outbound construction. `STATIC_HEADER` may use a non-reserved credential header such as `X-API-Key`, but may not use `Authorization` (use `STATIC_BEARER`), hop-by-hop/framing/Host/correlation/forwarding/cookie fields, or any `X-Gateway-*` field. The caller's field with the same managed credential name is always discarded, even if listed in the route allowlist. A missing/decrypt-invalid active credential fails closed; no empty or ciphertext fallback is sent.

For V1, a **sensitive custom caller header** is any non-mandatory-denied name containing a hyphen-delimited component `auth`, `authorization`, `token`, `secret`, `password`, `credential`, or `key`, or the exact name `api-key`. Examples include `X-Auth-Token`, `X-API-Key`, and `X-Secret`. Such a field is dropped by default and may be forwarded only if its exact name is explicitly included in the route allowlist and it is not the managed credential's header. This is a forwarding decision, not permission to log or audit its value. Reserved/mandatory-denied names remain unallowlistable regardless of pattern.

The default application headers `Accept`, `Content-Type`, and `User-Agent` are forwarded when present and otherwise eligible. `Content-Type` is forwarded only for an actual request body; M4 does not synthesize a JSON type. `Content-Encoding` and `Accept-Encoding` are not in the default list; a route may explicitly allow them, but the proxy must then preserve encoded entity bytes and avoid transparent decompression/recompression inconsistencies. The HTTP client must not silently introduce conflicting caller-visible encoding/framing. Other content/conditional headers require explicit route allowlisting. There is no route-configured literal outbound header support in M4 V1; adding one requires a new contract.

For an allowlisted non-singleton field, repeated inbound field lines are preserved as separate values in original order; do not silently comma-join them. Duplicate singleton `Content-Type` or `Content-Encoding` values are rejected as `400 invalid_request` before forwarding. Duplicate forbidden fields are stripped, except invalid/ambiguous framing or authentication syntax is rejected by the existing HTTP/auth boundary. A duplicate configured allowlist name is invalid at Admin write time. A malformed field name/value containing CR, LF, or forbidden control characters is rejected at the HTTP boundary as `400 invalid_request`; no route policy can legalize it. This contract imposes no new numeric header-size ceiling; bounded parser/server limits remain an implementation/deployment concern and must not be bypassed.

## 4. Response filtering

The upstream-to-client policy is a **fixed platform allowlist**, not the route JSON list. Forward only valid instances of: `Content-Type`, `Content-Encoding`, `Content-Language`, `Content-Disposition`, `Cache-Control`, `Expires`, `ETag`, `Last-Modified`, `Vary`, `Location`, `Retry-After`, `Accept-Ranges`, `Content-Range`, and `Allow`. Preserve repeated allowed field lines where legal; do not combine semantically non-combinable values. Preserve raw response entity bytes with `Content-Encoding`; do not forward an encoding header with a decoded body. Do not forward upstream `Content-Length` blindly: downstream framing must be derived from the bytes actually sent, or omitted for streaming. Gateway sets canonical `X-Request-ID` on every response.

All other upstream fields are stripped by default, including `Set-Cookie`, `Server`, `Via`, `X-Powered-By`, `X-Internal-*`, `WWW-Authenticate`, `Proxy-Authenticate`, `Proxy-Authorization`, `Connection` and nominated fields, `Keep-Alive`, `TE`, `Trailer`, `Transfer-Encoding`, and `Upgrade`. Route policy cannot allow response fields. Upstream `Set-Cookie` is not supported in M4 V1 and each instance is stripped. Upstream `Location` is forwarded **unchanged**, including an absolute backend URL, as explicitly frozen by the M4 pack; the Gateway does not follow it or rewrite it. This intentional exposure risk must be addressed by upstream/deployment configuration or a later explicit Location-rewrite contract, not by silently changing M4 V1 behavior.

Malformed upstream header syntax or CR/LF injection must not be sent downstream. Before response commitment, treat it as a safe normalized upstream protocol failure under the existing Gateway error contract; after commitment, terminate delivery rather than fabricate a second status/body. An otherwise valid but non-allowlisted response field is silently stripped. `Content-Type` is retained when safe so non-JSON/binary responses remain interpretable. Body/status semantics and circuit classification remain governed by their own contracts.

## 5. Normative examples

| Case | Exact M4 V1 behavior |
| --- | --- |
| `header_policy=NULL`, caller sends `Accept`, `Content-Type`, `User-Agent`, `X-Debug` | Forward the first three if applicable; drop `X-Debug`. |
| Route `{"request_allowlist":["accept"]}` and caller `Accept: application/json` | Forward `Accept`; default `Content-Type`/`User-Agent` are not inherited. |
| Unknown caller `X-Client-Trace` under NULL policy | Drop; explicit route allowlist is required. |
| Caller `Authorization: Bearer gw_...` | Authenticate locally, then strip; never send it upstream. Managed backend auth, if configured, is injected separately. |
| Caller `Host: attacker.example` | Strip; outbound `Host` derives from validated service authority. |
| Caller `Connection: X-Hop` plus `X-Hop: value` | Strip both, even if `X-Hop` is allowlisted. |
| Caller `X-Forwarded-For: 1.2.3.4` | Strip; do not append or regenerate in M4 V1. |
| JSON request with body and `Content-Type: application/json` under NULL policy | Forward the content type and raw body; derive outgoing length/framing. |
| Upstream `Set-Cookie: session=...` | Strip every `Set-Cookie`; no browser-session propagation. |
| Upstream `Location: https://backend.internal/next` | Forward unchanged; do not auto-follow or rewrite. |
| Route allowlist names `X-API-Key`, managed STATIC_HEADER also uses `X-API-Key` | Discard caller value; inject only the decrypted managed value. |

## 6. Compatibility, required reconciliation, and security

The route JSONB column can represent the chosen shape: **no database migration** is required. NULL rows remain usable with the safe default. `{}` and previously accepted arbitrary objects (for example the current Admin integration fixture `{"mode":"metadata-only"}`) become invalid for runtime use; they must be identified and explicitly corrected by an audited Admin configuration change before M4 traffic is enabled. This document neither claims the deployed database contains such rows nor silently rewrites them. The current Admin Pydantic schema accepts `dict | None`, the service stores it without semantic validation, and the frozen OpenAPI `RouteCreate`/`RoutePatch` properties permit arbitrary object keys. **OPENAPI/API RECONCILIATION REQUIRED before M4 runtime implementation:** tighten both Admin write validation and the public Admin schema to this exact object/null shape, with consistent 400 `invalid_request` behavior; update the existing permissive fixture/test in that later task. No OpenAPI file is changed here.

Route header policy is part of the authoritative route configuration resource. Any M4 route cache/current-state consumer must load it and follow M3-R3A invalidation/reconciliation completeness rules; no separate header-policy consumer is introduced. Existing M2.6 route CRUD, M4-R1 path routing, M4-R2 circuit classification, and future M5/M6 LLM behavior are otherwise unchanged.

Operational logs, metrics, audit records, and HTTP errors never include raw sensitive header values, Gateway `gw_` keys, upstream credentials, ciphertext, or uncontrolled exception text. M3-R13's bounded-dimension and identifier rules remain in force. Audit may record only bounded policy decision categories and, where appropriate under the existing audit schema, safe header **names/counts** after review; it must never record values. The mandatory stripping and validation rules guarantee that caller Gateway credentials, forged forwarding chains, hop-by-hop fields, and caller authority cannot be made forwardable by route policy. HTTP parser and HTTPX validation must reject CR/LF injection; they are not a substitute for this contract's explicit filters.
