# M4-R8 — Normal API Concurrency Lease Renewal Contract

Status: **FROZEN M4 V1 CONTRACT; READY FOR M4 CONCURRENCY RENEWAL IMPLEMENTATION.** Documentation reconciliation only. No runtime, test, OpenAPI, or migration change is made here.

## 1. Authority and scope

[M3-R3](Enterprise_AI_API_Gateway_M3-R3_Leased_Concurrency_Semaphore_Contract_Reconciliation.md) fixes the renewable atomic semaphore, deployment `concurrency_lease_duration_ms` (default 30,000; range 5,000–120,000), expiry, and no-resurrection rule, while assigning request lifecycle and renewal timing to later workload packages. [M3-R10](Enterprise_AI_API_Gateway_M3-R10_Protection_Handle_Provenance_Contract.md) routes renewal/release only to the issuing Redis backend or issuing local generation. The recovery-aware `RecoveryConcurrencySemaphore.renew` returns `renewed=false` for an invalid/unknown handle or missing local generation; for a Redis-issued handle it invokes Redis only and propagates a typed `ConcurrencyDependencyError` after marking Redis unreachable. It does **not** synthesize a local replacement lease. The Redis and local primitives return `renewed=false` for absent/expired ownership and extend an active lease by one configured duration from their own authoritative operation time.

[M4-R7A](Enterprise_AI_API_Gateway_M4-R7_Normal_API_Protection_Admission_Ordering_Contract.md) fixes acquire-after-rate/before-body, request-scope ownership, probe-safe admission, and one terminal release attempt. [M4-R9](Enterprise_AI_API_Gateway_M4-R9_Normal_API_Cancellation_and_In_Flight_Abort_Contract.md) fixes definitive-loss cancellation, the single terminal-decision coordinator, 500 `gateway_internal_error` before response commitment, post-commit delivery termination, circuit classification, and stop/await-renewal-before-release ordering. This contract fills only renewal lifecycle, cadence, and bounded UNKNOWN behavior. It does not redefine M3's algorithm, M4-R7A ordering, M4-R9 cancellation, upstream timeout, retry/fallback, SSRF, or TLS.

## 2. Owner, start, and active lifetime

The one Normal API request-execution scope that owns a successfully acquired **real** concurrency handle also owns its one renewal worker. It starts and supervises that worker immediately after acquisition is confirmed and before entering the bounded body guard. No worker is created after denied acquisition or for the empty-policy/null handle; neither case has a release obligation. There is no global scheduler, detached task, cross-request owner, or cross-process renewal handoff.

Concurrency ownership and renewal remain active from successful acquisition through the single M4-R9 terminal decision and cleanup. Covered phases are bounded inbound body reading/buffering, deterministic local preparation, circuit admission, HTTPX connect/write/read, upstream response wait, bounded generic downstream response streaming, and downstream delivery until execution terminalizes. Upstream headers alone do not end renewal. A short request that ends before the first scheduled renewal makes no unnecessary renew call but still attempts one terminal release. A long healthy request renews across multiple original TTL periods; lease expiry is not its normal completion path.

## 3. Deterministic cadence and conservative horizon

Let `T = concurrency_lease_duration_ms`, the existing validated M3 deployment value. All M4 scheduling uses a **monotonic local clock** and duration arithmetic; no wall-clock timestamp, jitter, new setting, or per-request/tenant override is introduced. M3 Redis `TIME` and local-store time remain authoritative for actual lease validity. M4's local schedule is only a conservative safety bound, not a claim to know the precise server expiry.

For each confirmed successful acquire or renewal, record `anchor` as the monotonic time **immediately before dispatching that successful operation**, not its later response time. Redis/local assignment occurs after dispatch, so `anchor + T` is a conservative earliest-expiry estimate in elapsed-time terms. Initial acquisition uses its dispatch-time anchor. If an operation returns so late that the safety deadline below has already arrived, do not treat the delayed response as permission to keep executing; terminalize conservatively. Clock discontinuity or inability to maintain a valid monotonic anchor is an internal terminal fault, not proof of backend lease loss.

The normal next renewal is due at `anchor + T/3`. The hard ownership-confidence deadline is `anchor + 2T/3`, leaving at least `T/3` of nominal TTL as scheduler/transport margin. At the frozen 5,000–120,000 ms TTL range, the corresponding normal intervals are 1,666.667–40,000 ms and deadlines are 3,333.333–80,000 ms after anchor; implementations should compare monotonic deadlines at native clock precision rather than round a scheduled delay upward past its deadline. Pure fractional scheduling is sufficient; no extra minimum/maximum clamp is introduced. Every in-flight renew operation is bounded by the same safety deadline. A scheduler stall, slow dependency call, or late result cannot extend the previous anchor's confidence window.

On `renewed=true` received before the applicable safety deadline, M3 has extended exact issued ownership; record the dispatch-time anchor of that successful renewal and schedule the next `anchor + T/3` check. There is no client-visible effect and no per-cycle success log requirement. If the new due time has already arrived, run the next check promptly, subject to the new safety deadline; never spin a tight loop or start overlapping renew operations. Only one renewal call for the handle may be in flight at a time.

## 4. Definitive loss and UNKNOWN dependency results

`renewed=false` is definitive concurrency ownership loss under M4-R9. The worker signals the request's single terminal-decision coordinator immediately. If loss wins, request-scoped upstream/delivery is cancelled under M4-R9, no new circuit admission occurs if still pre-circuit, and circuit completion follows only an already recorded definitive M4-R2 upstream outcome. The shared HTTPX client stays alive. The original handle remains the only handle for terminal cleanup.

A typed `ConcurrencyDependencyError` or equivalent frozen M3 dependency failure during Redis-issued renewal is **UNKNOWN**, not `renewed=false`; do not misreport it as confirmed backend loss, create local ownership, switch provenance, or silently continue forever. On the first UNKNOWN for a given confirmed anchor, keep the request active provisionally and schedule **one** early retry at `anchor + T/2`, or immediately if that time has already passed. Never run overlapping calls or retry before the first call has returned. The retry uses the same policies, same issued handle, and same issuing backend. An UNKNOWN retry does not change the anchor. A true retry result starts a new confirmed anchor; a false result is definitive loss. If the retry is UNKNOWN again, wait only until the existing hard deadline; no further retry is required in that confidence window. This is a bounded M4 renewal retry, **not** a retry of the upstream request.

If no confirmed successful renewal exists when monotonic time reaches `anchor + 2T/3`, the request terminalizes through M4-R9's local ownership-safety cancellation path, including when a dependency call remains unresolved. This is **unverified ownership beyond the permitted confidence window**, not an assertion that Redis returned false or that the backend lease has already expired. The same pre-commit 500 `gateway_internal_error` or post-commit stream termination applies; no new public status is introduced. The pending renewal call is stopped/awaited before release, and a late result must not revive or re-terminalize the request. A direct `renewed=false` terminalizes earlier. The worker must also enforce the deadline when the scheduler is delayed or a call hangs; a slow or failed dependency cannot keep an active request beyond it.

Before circuit admission, either definitive loss or expiry of the UNKNOWN confidence window prevents circuit admission and any HALF_OPEN claim. After circuit admission, it invokes M4-R9 cancellation; a local cancellation with no definitive upstream outcome makes no M3 circuit success/failure call, and an owned HALF_OPEN probe remains under existing M3 expiry. If the upstream outcome won the M4-R9 race first, preserve that classification exactly once even if downstream delivery is later terminated. Do not infer an upstream failure from renewal uncertainty.

An unexpected renewal-worker programming/contract exception is a terminal **internal fault**, never disguised as a Redis UNKNOWN. Unexpected worker cancellation while the request is still active is likewise terminal. The worker reports that fault to the same request-owned coordinator, which ends request-scoped work with the existing safe internal-error boundary and one cleanup path. An intentional stop after a terminal decision is not a second fault. The request must never silently outlive a dead worker until lease expiry.

## 5. Terminal coordination, provenance, and lifecycle

The renewal worker communicates results and faults to M4-R9's one terminal coordinator; it never independently sends an HTTP response, completes a circuit, or releases concurrency. The request scope records the terminal decision, stops/cancels renewal, **awaits worker termination**, then attempts exactly one provenance-aware release for the original real handle and finishes remaining request cleanup. A successful renewal cannot race after release, and no renewal may start once terminalization is recorded. The terminal owner also cancels/awaits request-scoped upstream work and closes any acquired response according to M4-R9. This contract defines ordering, not a second terminalization path.

Release remains required once after definitive `renewed=false`, UNKNOWN-window expiry, or an internal worker fault. M3-R3 safely returns `released=false` for missing/expired ownership and may remove exact caller-owned partial residue; M3-R10 forbids retrying release on a different backend. Release failure does not replace an already committed public result or cause a second attempt. A short request has the same release obligation even if no renewal ran. On client disconnect or graceful-shutdown request termination, M4-R9 ends the scope, stops/awaits renewal, and runs the same release path. No renewal task survives its request scope and no distributed handoff is introduced.

The worker is request/process-local. Redis semaphore state remains shared authority across processes; local degraded generations remain process-local under M3-R9/R10. A Redis-issued handle never becomes local because Redis is unavailable. A local-generation handle continues renewal against its issuing generation after cutover, or returns false under existing stale/expired semantics. M4 does not construct a new handle from current traffic mode.

## 6. Compatibility, observability, and required later tests

No new deployment setting, Redis key, database field/table/migration, OpenAPI operation/status/error code, or M3-R3A required configuration consumer is introduced. The M4-R9 pre-commit 500 and post-commit termination rules remain authoritative. M3 lease TTL is startup/runtime protection configuration, not a tenant current-state consumer. The existing service/route M3-R3A consumer remains a separate M4 readiness gate.

Record bounded, sanitized categories for definitive renewal loss, first UNKNOWN dependency result, recovery after UNKNOWN, UNKNOWN-window expiry, and internal worker fault. Per-cycle successful renewals need not be logged. Correlate operational logs with canonical request ID; use tenant/service correlation only where existing telemetry schema permits it, never as high-cardinality metric labels. Do not log bodies, raw headers/URLs/queries, Gateway or upstream credentials, raw lease/probe IDs, Redis keys, or raw exception text. No new metrics infrastructure or audit action is authorized.

Later controlled-clock unit tests must prove: no worker for denied/null acquisition; start immediately after a real acquire and before body guard; `T/3`, `T/2`, and `2T/3` deadlines at 5,000 and 120,000 ms; no upward rounding past deadline; renewal before original expiry; multiple true renewals; short-request cleanup; direct false terminalization; one UNKNOWN then successful retry; repeated UNKNOWN to deadline; a hanging call cut off by deadline; a delayed success after deadline not reviving execution; no overlapping renewals; and worker-internal error propagation. Assert no circuit admission after pre-circuit terminal loss, M4-R9 in-flight abort after post-circuit loss, no fabricated circuit failure, renewal during downstream delivery, stop/await before one release, no renew after release, and no orphan worker after disconnect/shutdown. Prove Redis-issued renewal never switches to local and local-generation renewal remains with its issuing generation across recovery cutover.

Local-only acceptance uses a synthetic upstream and a short configured lease with concurrency limit one. Hold the first request active beyond its original TTL; multiple confirmed renewals keep its slot, so a competing request is denied. Finish the first request, verify the worker stops and exactly one release occurs, then admit a subsequent request. A controlled facade-fault variant injects one UNKNOWN followed by a true retry and separately repeated UNKNOWN through the hard deadline; verify continued provisional operation only inside the safety window and M4-R9 cancellation at its end. No external network or arbitrary sleep is required for the correctness assertions.

## 7. Narrow supersession

M4-R8 qualifies M4-R7A's explicitly deferred renewal timing and supplies M4-R9's bounded handling input for UNKNOWN renewal results. It preserves M3-R3 acquisition/renewal/expiry semantics, M3-R10 provenance, M4-R7A admission order/rate/body/circuit behavior and one release obligation, and M4-R9 cancellation, terminal race, and client result. It defines neither timeout values nor M6 retry/fallback, SSRF, or TLS policy.
