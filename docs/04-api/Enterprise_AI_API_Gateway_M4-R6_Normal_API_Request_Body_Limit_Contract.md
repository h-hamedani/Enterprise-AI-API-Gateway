# M4-R6 — Normal API Request Body Limit Contract

Status: **FROZEN M4 V1 CONTRACT; API/OPENAPI RECONCILIATION REQUIRED before runtime implementation.** This document changes no runtime, Admin API, OpenAPI, database, or test artifact.

## 1. Authority and narrow scope

The [API Specification V1.2.2 Final](Enterprise_AI_API_Gateway_API_Specification_V1.2.2_Final.docx) fixes the Normal API default at 10 MiB, requires a configurable deployment policy, and maps excess bodies to HTTP 413 `request_too_large`. The [OpenAPI 3.1 V1.2 Final](Enterprise_AI_API_Gateway_OpenAPI_3.1_V1.2_Final.yaml) records `defaultRequestBodyLimitBytes: 10485760` and the existing error vocabulary. The [M4 Execution Pack V1.1](../05-implementation/Enterprise_AI_API_Gateway_M4_Normal_API_Engine_Execution_Pack_V1.1.docx) calls the deployment limit a configurable ceiling, requires immediate rejection when `Content-Length` proves excess, and requires counting bodies of unknown/chunked length. The current physical model and M1 migration contain non-null positive `normal_api_services.request_body_limit_bytes`; the M2 registry currently writes 10,485,760 on create but neither accepts nor returns the field. The current `Settings` model has no body-limit setting. [M3-R3A](Enterprise_AI_API_Gateway_M3-R3A_Configuration_Consumer_Reconciliation_Completeness_Contract.md) governs any required cached configuration consumer. [M4-R1](Enterprise_AI_API_Gateway_M4-R1_Normal_API_Routing_Path_Resolution_Contract.md), [M4-R2](Enterprise_AI_API_Gateway_M4-R2_Normal_API_Circuit_Outcome_Classification_Contract.md), [M4-R3](Enterprise_AI_API_Gateway_M4-R3_Normal_API_Header_Policy_Contract.md), [M4-R4](Enterprise_AI_API_Gateway_M4-R4_Normal_API_Header_Policy_Admin_OpenAPI_Contract.md), and [M4-R5](Enterprise_AI_API_Gateway_M4-R5_Upstream_HTTP_Client_Pool_Contract.md) retain their scopes.

This addendum freezes body-size ownership, configuration, computation, enforcement, and Admin representation only. It does not decide response-size limits, timeout, redirect, TLS, SSRF, retry, fallback, or upstream streaming policy.

## 2. Ownership, defaults, and precedence

M4 V1 has **both** a startup-only, per-process deployment safety ceiling and a persisted, tenant-owned per-service limit. The service value is real runtime configuration, not an unused transitional column. For a resolved service in a particular process:

`effective_limit_bytes = min(NORMAL_API_REQUEST_BODY_LIMIT_BYTES, normal_api_services.request_body_limit_bytes)`.

The shared product default is exactly **10,485,760 raw body bytes (10 MiB)**. Both the absent deployment setting and a newly created service whose Admin create request omits the field use this one documented product-default value; they are not independent policies that happen to share a number. The existing hard-coded creation value and ORM default express that same default. A deployment ceiling raised above 10 MiB does not implicitly increase existing or newly defaulted service limits: an explicit service Admin change is also necessary. A lower deployment ceiling immediately caps every service in that process after restart. Service values may exceed the local deployment ceiling; they are valid and retained for configuration portability, but never raise the effective limit above that ceiling. There is no automatic clamp or persisted rewrite.

The deployment setting is `NORMAL_API_REQUEST_BODY_LIMIT_BYTES`, mapped by the existing case-insensitive `Settings` mechanism to `normal_api_request_body_limit_bytes`; no alias, tenant row, or dynamic setting endpoint is added. It is optional, defaulting to 10,485,760, and changes require application process restart. All processes in one deployment should be configured consistently; M4-R6 adds no cross-process coordinator.

## 3. Exact bounds and validation

The approved M4 V1 configurable range for **each** deployment and service value is **1 through 67,108,864 bytes inclusive (1 byte through 64 MiB)**. This 64 MiB operational ceiling is a new M4-R6 safety decision, not a claim that the earlier artifacts specified it. Zero, negative, null, fractional, malformed, and above-maximum values are invalid. An empty request body is nevertheless valid: the minimum constrains configured limits, not body length. A value equal to the deployment ceiling is valid; a service value above that ceiling is valid when it remains within its own 64 MiB maximum.

Absent deployment configuration uses the product default. An explicitly invalid deployment value fails configuration validation and application startup; it is never clamped, silently defaulted, or converted into an HTTP request error, M3 circuit outcome, or Redis degraded-mode event. Typed integer configuration follows the existing `Settings` integer parsing convention, without a new canonical-text rule. The existing service column is non-null `BIGINT`, has an ORM default of 10,485,760 and a positive database check, but the Alembic column has **no server default**. Admin creation must continue to insert an explicit value. Admin create/PATCH rejects invalid inputs before mutation with the existing `400 invalid_request` envelope, with no successful audit, config-version increment, or invalidation event.

## 4. Admin create, PATCH, and read contract

The service Admin resource gains `request_body_limit_bytes` as an integer in the approved range.

| Operation | Omitted | Explicit `null` | Valid integer |
| --- | --- | --- | --- |
| `ServiceCreate` | Persist 10,485,760 | Reject `400 invalid_request` | Persist supplied value |
| `ServicePatch` | Preserve existing value | Reject `400 invalid_request` | Replace stored value |
| `Service` GET/list/create/PATCH response | Never omitted | Never null | Return the **stored service value**, not the process-specific effective minimum |

Create does not inherit the deployment ceiling. PATCH changes this field through the existing tenant-scoped service mutation transaction, audit action, config-version increment, and post-commit invalidation path. The response does not expose the effective value, which can differ among processes if deployment settings differ. The new field is not write-only. Unknown or non-integral JSON types and values outside the approved range receive existing validation errors; do not add an error family. A service value above a deployment ceiling is **not** an Admin validation error, because the effective minimum remains bounded and the stored configuration is portable.

The current OpenAPI `ServiceCreate` and `ServicePatch` schemas must add an optional, non-null integer property with `minimum: 1`, `maximum: 67108864`, and a description of omission/null and `min(deployment, service)` behavior. `Service` must add that same integer property to both `properties` and `required`; all service response forms use it. This is a narrow Admin API/OpenAPI addendum to the frozen V1.2 source, analogous to M2.6/M4-R4 reconciliation. The dynamic public Normal API path and existing 413 error envelope need no new operation or error code. Generated FastAPI OpenAPI and static OpenAPI must be reconciled in the later API implementation; neither is edited here.

## 5. Enforcement and forwarding boundary

Resolve the effective limit only after the Gateway key has established tenant context and the ACTIVE service/route and permission have been resolved; the service is the source of the persisted value. The M4 pack places M3 protection and circuit admission before the body guard. This contract does not rearrange those stages or decide the internal order of rate and concurrency checks. Thus a request eventually rejected with 413 may already have incurred an applicable rate charge or acquired a concurrency handle, which must be released through its existing lifecycle. It has **no definitive upstream outcome** and makes no M3 circuit success/failure completion call. An earlier authentication, authorization, rate, or OPEN-circuit denial may take precedence without reading the whole body.

Measure the exact number of raw body bytes delivered by ASGI, not JSON characters or a decompressed representation. M4 introduces no automatic request decompression. If an explicitly permitted `Content-Encoding` is forwarded under M4-R3, the entity bytes used for the count and forwarded upstream must remain consistent; this contract does not authorize a decompression/recompression transform. Apply the limit to any supported Normal API method carrying a body, including GET and DELETE, not only POST/PUT/PATCH. Exactly `effective_limit_bytes` is accepted by the size gate; the next byte causes 413. An empty body passes this gate.

For a valid, unambiguous `Content-Length` greater than the effective limit, respond immediately with 413 without consuming the whole body or opening an upstream request. A missing length, chunked body, or an understated length where the HTTP server permits it cannot bypass enforcement: count actual ASGI-delivered bytes and reject at limit + 1. Invalid/conflicting framing follows M4-R3's `400 invalid_request` rule rather than being trusted as a size bypass. In M4 V1, **all** bodies must pass bounded size preflight before upstream request creation: an eventual 413 results in zero upstream I/O, even for unknown/chunked lengths. This is compatible with the pack's requirement to abort oversized streaming input; it is stricter about not beginning upstream transfer. No unbounded read or buffer is permitted. In-memory buffering up to the effective bound is allowed, as is a bounded spool; the implementation strategy is not frozen here. This is inbound size enforcement, not a decision to implement M6 upstream streaming.

Return the existing Gateway error envelope with HTTP **413**, `error.type`/`error.code` **`request_too_large`**, safe message **“Request too large.”**, canonical `request_id`, and `X-Request-ID`. Do not turn an oversized inbound request into upstream failure, circuit failure, or a second 413 schema. No upstream credential is needed or decrypted for a rejected body.

## 6. Configuration reconciliation, data, and privacy

The current code has **no registered Normal API service/route runtime consumer**. M4's service current-state consumer, when introduced for runtime configuration, must include `request_body_limit_bytes` in the authoritative service snapshot and be a required M3-R3A consumer with `reconcile_current_state(tenant_id)`. Do not create a separate body-limit consumer. A committed Admin change participates in the existing service audit/config-version/post-commit invalidation transaction; if event delivery or a required callback fails, M3-R3A dirty/pending reconciliation rules apply. A process must not treat version equality alone as proof of current body-limit state. The deployment ceiling itself is startup-only and is **not** an M3-R3A consumer.

No database column, type, enum, or migration is required to represent the policy. The existing positive check protects against zero/negative values. The new 64 MiB upper bound is an Admin/runtime contract rather than a new database check: the per-process deployment ceiling is also at most 64 MiB, so even a directly inserted larger positive value cannot increase the effective runtime limit. Nevertheless, a persisted out-of-range service value is invalid configuration: runtime fails closed before upstream I/O; Admin reads and unrelated PATCH must not report or preserve it as valid; an explicit audited PATCH setting an in-range value may repair it. No automatic clamp or data rewrite is authorized. The inspected local PostgreSQL database contained **zero** `normal_api_services` rows at reconciliation time; this is not a claim about other environments. Existing rows must be inventoried for null, zero, and above-maximum values before M4 traffic is enabled. The non-null/positive database constraints rule out null/zero in a valid migrated database, but not an above-maximum legacy/direct-write value.

An oversized rejection may be recorded with bounded outcome category, effective limit, and observed byte count where available under existing request telemetry. Existing authorized request/tenant/service correlation may be used where the established database telemetry schema permits it. Operational logs and metric labels follow M3-R13's bounded/redacted rules: do not include body bytes, decoded content, `gw_` key, managed upstream credential, raw headers, URL query, uncontrolled exception text, or high-cardinality tenant/service identifiers. This contract adds no metrics exporter, aggregate table, or new audit action. A rejected read-only proxy request does not become a Control Plane configuration audit mutation.

## 7. Required later tests and acceptance

The later Admin/settings implementation must test deployment default, valid 1 and 67,108,864 boundaries, malformed/non-integer/null/zero/out-of-range startup rejection, and no clamping; create omission/null/valid/excess, PATCH omission/null/valid/excess, stored response value, value above deployment ceiling, and no audit/version/invalidation on rejected Admin writes. Test existing-data invalid-row fail-closed/explicit repair without silent mutation, including direct-write above-maximum fixtures. Test the required service consumer's callback/reconciliation completeness when its service snapshot changes.

The later local-only runtime acceptance uses a synthetic upstream with no internet dependency. Prove default and custom limits, the effective minimum, exactly-at-limit admission, limit + 1 rejection, immediate `Content-Length` overflow, unknown/chunked overflow, understated length where supported, empty body, supported methods with bodies, and no upstream request or circuit completion on 413. Assert bounded memory/consumption behavior and existing normalized error output; ensure any acquired concurrency handle is released. Do not rely only on publisher mocks or a test that bypasses the actual gateway entry point.

## 8. Compatibility and supersession

M3 rate/concurrency algorithms and circuit identity/transitions do not change; M4-R2's `NO_COMPLETION` applies to body rejection. M4-R1 path/query selection, M4-R3/R4 header policy, and M4-R5 process-local HTTP client pool are unchanged. The body gate precedes outbound request construction and does not dictate M6 retry, fallback, response streaming, or future upstream request-streaming policy. No local body state is merged into Redis or shared across processes.

M4-R6 qualifies the M4 pack's “configurable deployment ceiling” and the existing service column with the exact two-limit model, defaults, bounds, precedence, Admin representation, and oversized-body enforcement above. It supersedes no earlier frozen routing, header, circuit, client-pool, timeout, transport-security, or response contract. **The Admin API and static/generated OpenAPI reconciliation must be implemented and verified before the Normal API runtime uses the new Admin-managed service limit.**
