# M4-R7 — Normal API Protection Admission Ordering Contract

Status: **M4-R7A CIRCUIT-PROBE-SAFE ORDERING RECONCILIATION.** Documentation only; no runtime, test, OpenAPI, or migration change is made here.

## 1. Authority, boundary, and narrow precedence

The [M4 Normal API Engine Execution Pack V1.1](../05-implementation/Enterprise_AI_API_Gateway_M4_Normal_API_Engine_Execution_Pack_V1.1.docx) places authenticated tenant/service/route/permission resolution before cumulative M3 rate checks, rate before circuit admission, and the body/timeout guard after circuit admission. It requires best-effort release of acquired concurrency on disconnect, but leaves acquisition placement unspecified. [M4-R6](Enterprise_AI_API_Gateway_M4-R6_Normal_API_Request_Body_Limit_Contract.md) originally preserved that body-guard boundary. **M4-R7A narrowly supersedes their circuit-before-body ordering:** a predictable local rejection must not claim the sole HALF_OPEN probe. The M4-R6 amendment states the same precedence explicitly; its other body-limit semantics remain frozen. [M3-R2](Enterprise_AI_API_Gateway_M3-R2_Atomic_Token_Bucket_Algorithm_Contract_Reconciliation.md) fixes cumulative atomic rate consumption; [M3-R3](Enterprise_AI_API_Gateway_M3-R3_Leased_Concurrency_Semaphore_Contract_Reconciliation.md) fixes atomic leased concurrency and its results; [M3-R4](Enterprise_AI_API_Gateway_M3-R4_Distributed_Circuit_State_Contract_Reconciliation.md), [M3-R4A](Enterprise_AI_API_Gateway_M3-R4A_Circuit_Configuration_Source_Contract_Reconciliation.md), and [M3-R4B](Enterprise_AI_API_Gateway_M3-R4B_Circuit_Generation_Eligibility_Token_Contract_Reconciliation.md) fix circuit identity and eligibility. [M3-R11](Enterprise_AI_API_Gateway_M3-R11_Unknown_Circuit_Completion_Result_Contract.md) and [M3-R12](Enterprise_AI_API_Gateway_M3-R12_Local_Circuit_Completion_Lifetime_Contract.md) govern completion provenance/lifetime. [M4-R2](Enterprise_AI_API_Gateway_M4-R2_Normal_API_Circuit_Outcome_Classification_Contract.md) maps actual upstream outcomes to completion; M4-R6 governs the body gate. Existing app state exposes recovery-aware rate, concurrency, and circuit facades but no Normal API proxy invocation yet.

M4-R7 fixes only orchestration stage order, denial precedence, and lease cleanup. It does not change any M3 primitive, local-degraded or recovery algorithm, body-size value, timeout, renewal, retry, fallback, streaming, SSRF, or TLS rule.

## 2. Normative M4 V1 sequence

For one supported Normal API request, the following is the single stage order. A rejection exits immediately; no later admission stage runs.

1. Establish the canonical Gateway request ID; authenticate the `gw_` key and bind its tenant/application/API-key identity. Reject unauthenticated or disabled/revoked identity before any Normal API protection admission.
2. Resolve one ACTIVE tenant-owned service by slug and one ACTIVE route by normalized remaining path and method; enforce route/service permission and fail closed on ambiguity or invalid required service/route configuration. Resolve and validate the service's persisted body-limit value and effective M4-R6 limit. Validate the stored M4-R3 route header-policy shape and request acceptance syntax required before admission; actual outbound header selection/injection occurs later. Do not query rate, concurrency, or circuit facades for unresolved, foreign-tenant, disabled, unauthorized, or malformed configuration.
3. Evaluate all applicable enabled Normal API **request-rate** policies together through the M3 facade, in M3-R2's deterministic `API_KEY`, `ROUTE`, `SERVICE` input order. On denial, return the existing `429 rate_limit_exceeded` result (including the M3 maximum rejecting retry delay where applicable), and stop.
4. Acquire all applicable enabled Normal API **concurrency** policies together through the M3 leased-concurrency facade, in M3-R3's `API_KEY`, `ROUTE`, `SERVICE` input order. This is the **only** acquisition point: rate has allowed; no circuit admission or body read has yet occurred; no upstream HTTPX request object or connection exists. On capacity denial, stop with `429 rate_limit_exceeded`, without a lease, circuit call, body read, or upstream I/O. No `Retry-After` is synthesized from concurrency denial because M3-R3 supplies no retry delay. An empty policy set retains M3-R3's neutral acquired result with a null lease ID and no releaseable ownership.
5. Run the M4-R6 bounded request-body guard, including immediate valid-`Content-Length` overflow rejection and actual-byte counting for unknown/chunked bodies. Reject an oversized body with `413 request_too_large`, zero circuit admission, zero upstream I/O, no circuit completion, and release any actual concurrency lease.
6. Complete all deterministic local validation and pre-upstream request preparation that can fail without upstream I/O, including bounded body buffering, header-policy enforcement, query/path construction validation, and locally constructible outbound request validation. A local failure returns its applicable existing Gateway error, releases any actual concurrency lease exactly once, and invokes neither circuit admission nor upstream I/O nor circuit completion. This stage does not decide still-unresolved SSRF, DNS, TLS, timeout, or error-taxonomy details; those remain for their own contracts. Where technically possible, their deterministic local checks must precede a probe claim. Do not create an upstream connection here.
7. As the final protection gate immediately before upstream execution, invoke M3 circuit eligibility/claim for the resolved tenant + route + V1 service backend identity. On OPEN/occupied-HALF_OPEN denial, return `503 upstream_unavailable`, make no circuit completion call, and release any actual concurrency lease acquired at stage 4. A successful HALF_OPEN claim is exclusive M3 probe ownership; immediately proceed to the single upstream attempt without another ordinary deterministic local validation stage.
8. Make one M4 V1 upstream attempt. Classify a definitive upstream outcome under M4-R2 and invoke its applicable provenance-aware circuit completion at most once. A gateway-side denial or fault before a definitive upstream outcome invokes no circuit success/failure completion. Terminal request-execution cleanup attempts release of an actual acquired concurrency lease exactly once, including when execution ends abnormally.

This order places **rate → concurrency → body gate → deterministic local preparation → circuit → upstream attempt** after authentication/resolution. The first rejecting stage wins. The body is not read for an earlier rate or concurrency denial. Bounded body bytes are consumed before circuit admission and before any upstream I/O. A deterministic body or preparation rejection cannot claim a HALF_OPEN probe. Residual exceptional failure after a successful circuit claim but before actual socket I/O remains `NO_COMPLETION` under M4-R2 and subject to existing M3 probe expiry; M4 fabricates neither an outcome nor an abort primitive. The pipeline minimizes that window by completing ordinary local preparation before claiming the probe.

## 3. Precedence and side effects

The first rejecting stage in Section 2 determines the client response. Authentication, tenant-scoped resolution, route permission, and required configuration validation precede the protected stages. Precedence is **rate (429) → concurrency (429) → body/local-preparation rejection → circuit (503) → upstream outcome/error**. An oversized body returns `413 request_too_large`; a deterministic preparation failure uses its applicable error contract, without inventing a code here. An earlier rejection invokes no later facade, obtains no later lease/probe, creates no upstream request, and mutates no later protection state.

Successful M3-R2 rate evaluation consumes one request cost in every applicable bucket even if later concurrency, body, local preparation, or circuit checks reject; **no refund** exists in M3-R2 and M4 introduces none. Rejected rate evaluation deducts no request cost from any layer, apart from M3-R2's permitted refill-state persistence. A successfully acquired concurrency lease may briefly occupy capacity while the body guard, local preparation, or circuit admission runs, and must then be released on denial. A body 413 or ordinary deterministic pre-upstream preparation failure invokes no circuit eligibility call and cannot claim a HALF_OPEN probe. A circuit eligibility check may materialize CLOSED state or claim a HALF_OPEN probe under M3-R4 only after that preparation has succeeded; M4 does not undo those admission-side effects.

This contract maps ordinary concurrency **capacity denial** to the already-existing `429 rate_limit_exceeded` Gateway error family. It does not convert typed Redis dependency failures, invalid policy/configuration, or internal faults into a capacity denial. Those follow the existing M3-R7/M3.9 and Gateway failure boundaries. The current M4 pack enumerates 429 for a protection limit but does not separately name concurrency denial; this is a narrow M4 HTTP mapping, not a new public code or M3 semaphore result.

## 4. Concurrency ownership and terminal release

The M4 request-execution scope owns the provenance-aware M3 concurrency handle returned by a successful non-empty-policy acquire. Neither HTTPX, the circuit facade, nor an untracked background task receives ownership. The scope records one release obligation for that actual handle. It makes **at most one release attempt**, only after successful acquisition with a non-null handle, and never for an acquisition denial or M3's empty-policy null handle. Nested cleanup, error handlers, and response finalizers must share that one obligation rather than each releasing. The M3 facade routes release to the issuing Redis or local generation, including across recovery cutover; M4 must not reconstruct a raw lease or choose a backend from current mode.

Terminal cleanup must attempt release after: circuit denial; body 413; outbound request construction/credential/header/configuration failure after acquisition; upstream transport failure; completed upstream response (including upstream 5xx); gateway/internal exception; and any request-execution exit after acquisition. When response delivery remains active, the request execution still owns the obligation; header commitment alone is not a terminal release. If the downstream disconnects or cancellation ends execution, cleanup retains the same best-effort obligation. This is only the minimal cleanup invariant; detailed cancellation propagation and lease-renewal scheduling are deferred.

M3-R3 release is idempotent by handle and returns `released=false` for missing, expired, stale, or already released ownership; M3-R9/R10 preserve provenance across mode changes. A failed/false release, or a typed release dependency failure, does **not** replace an already determined public response or trigger a second release in another backend. Record only a bounded, sanitized release-outcome category under M3-R13; do not log lease IDs, Redis keys, raw exceptions, tenant/resource IDs as metric labels, or credentials. M3 lease expiry/pruning is the safety net, not permission to omit the best-effort attempt. This contract adds no release-retry worker, lease registry, or compensation transaction.

Circuit admission is separate from completion. Rate, concurrency, body, local-preparation, or circuit rejection never becomes an upstream circuit success/failure. Once an actual upstream outcome is definitive, M4-R2 controls its one classification/completion attempt; M3-R11/R12 may return stale/unknown handle without a fabricated state. Release still occurs irrespective of circuit completion result or failure.

## 5. Acceptance and compatibility

Later tests must use call-order spies/fakes around the rate, concurrency, circuit, and HTTPX facades, plus a local synthetic upstream for integrated HTTP behavior. Assert both the returned error and absence of later calls/upstream I/O in each pairwise conflict:

| Simultaneous potential denials | First result | Later stages not invoked |
| --- | --- | --- |
| Body oversized + rate exhausted | 429 `rate_limit_exceeded` | Concurrency, body guard, circuit, upstream |
| Body oversized + concurrency exhausted (rate allows) | 429 `rate_limit_exceeded` | Body guard, circuit, upstream |
| Body oversized + circuit OPEN (rate/concurrency allow) | 413 `request_too_large` | Circuit admission, upstream |
| Rate exhausted + concurrency exhausted | 429 rate denial | Concurrency, body guard, circuit, upstream |
| Rate exhausted + circuit OPEN | 429 rate denial | Concurrency, body guard, circuit, upstream |
| Concurrency exhausted + circuit OPEN (rate allows) | 429 concurrency denial | Body guard, circuit, upstream |
| Valid body + circuit OPEN (rate/concurrency allow) | 503 `upstream_unavailable` | Upstream |

Also test authenticated/resolution/permission failures before any protection call; the exact M3-R2 one-shot cumulative rate side effect when a later stage rejects; no rate refund; empty-policy null-handle behavior; OPEN/occupied-HALF_OPEN denial after body/local preparation and acquire; body 413 after acquire with **no circuit admission or completion**; and no upstream connection before final admission. Assert absence of later-stage invocation, not just HTTP status. Given a free HALF_OPEN probe and an oversized body, rate and concurrency succeed, the body guard returns 413, circuit admission is never called, the probe remains free, concurrency releases exactly once, and no upstream request occurs. Also test a deterministic local preparation failure before circuit admission: no probe claim, no upstream I/O, and exactly one release attempt for an actual handle; defer any unfrozen error taxonomy.

Exactly-once release tests must cover successful upstream 2xx and 5xx, circuit denial, body 413, request-preparation exception, transport exception, internal exception, and minimal cancellation/disconnect exit. Assert no release on rate or concurrency denial, one release attempt for a real handle on every later exit, no double release through nested cleanup, safe behavior when release returns false or raises a typed dependency error, and issuing-backend provenance preservation across M3 mode change. Detailed disconnect propagation and lease-renewal timing have separate contract gates.

M4-R7 adds no table, column, Redis key, M3 algorithm, configuration consumer, or migration. It does not solve the pending M4 service/route M3-R3A current-state consumer; ordering alone introduces no new required consumer. The frozen OpenAPI already contains the `rate_limit_exceeded`, `request_too_large`, and `upstream_unavailable` error vocabulary, and the dynamic Normal API surface is represented by `x-gateway`; this ordering adds no response shape or operation. Precedence is acceptance-test behavior, so **no OpenAPI change** is required. Telemetry may record bounded stage/denial/release outcome categories and canonical request correlation under M3-R13; no body, credential, secret, raw exception, or high-cardinality identifier is added to logs or metric labels.

M4 V1 makes one upstream attempt; this contract does not define M6 retry/fallback or ownership for future attempts. **LEASE RENEWAL SEMANTICS ARE NOT DEFINED BY M4-R7.** A long-running request that can outlive the M3 lease TTL remains a separate later contract blocker; no heartbeat or TTL extension is inferred here. Timeout durations, pool-acquisition timing, response streaming, and detailed downstream cancellation also remain separate M4 gates.

M4-R7A narrowly supersedes the M4 pack's and M4-R6's **circuit-before-body** ordering, as explicitly amended in M4-R6, and fixes the previously unspecified concurrency-acquisition placement and resulting rejection/release precedence. It does not supersede M4-R6's effective limit, Content-Length and actual-byte rules, 413 envelope, zero-upstream-I/O guarantee, deployment/service precedence, Admin behavior, or buffering bound. It does not supersede M3-R2/R3/R4/R11/R12, M4-R1 through M4-R6A outside this ordering amendment, or any unresolved transport/security contract.
