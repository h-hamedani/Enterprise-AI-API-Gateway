# M4-R16 — Normal API Response Forwarding / Body-Forbidden Status Contract

Status: **FROZEN M4 V1 CONTRACT — DOCUMENTATION ONLY.** This contract narrows response/status/framing behavior, especially body-forbidden final responses. It does not implement streaming or a transport adapter.

## 1. Authority and response boundary

[M4-R2](Enterprise_AI_API_Gateway_M4-R2_Normal_API_Circuit_Outcome_Classification_Contract.md) classifies one definitive upstream outcome, including verified malformed protocol as `FAILURE`. [M4-R3](Enterprise_AI_API_Gateway_M4-R3_Normal_API_Header_Policy_Contract.md) fixes response-header filtering and forbids blindly forwarding upstream `Content-Length` or transfer framing. [M4-R9](Enterprise_AI_API_Gateway_M4-R9_Normal_API_Cancellation_and_In_Flight_Abort_Contract.md) fences definitive upstream outcome against cancellation and forbids a second downstream envelope after commitment. [M4-R10](Enterprise_AI_API_Gateway_M4-R10_Normal_API_Upstream_Timeout_Policy_Contract.md) ends its pre-response budget at the first committed downstream `http.response.start` and retains read-idle protection during generic streaming. [M4-R5](Enterprise_AI_API_Gateway_M4-R5_Upstream_HTTP_Client_Pool_Contract.md) owns the shared client, not individual response scopes.

HTTP/1.1 [RFC 9112](https://www.rfc-editor.org/rfc/rfc9112.html) determines message framing for HEAD, 1xx, 204, and 304 at the end of headers even if representation-length metadata is present. [RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html) allows conditional representation-length metadata on HEAD/304, forbids `Content-Length` on 204, and requires 205 to generate no content. M4 V1 uses these distinctions; it does not equate a nonzero metadata `Content-Length` with received content. The M4 execution pack supports GET/POST/PUT/PATCH/DELETE only, so public HEAD and CONNECT proxy operations remain unsupported. The HEAD rules below apply to any internal/wire-level HEAD response encountered in transport testing and do not add a public HEAD endpoint.

Only the single **final** upstream response is eligible for downstream status forwarding. Informational `100..199` is not a final response or circuit completion; M4 V1 does not forward separate informational responses downstream. `101 Switching Protocols`/upgrade is unsupported and retains M4-R2 `NO_COMPLETION`; it does not start a tunnel. A successful CONNECT tunnel is outside V1. Valid final status is forwarded unchanged, including ordinary non-2xx statuses, after response safety checks. Invalid/non-HTTP status is M4-R2 verified protocol `FAILURE`, not an ordinary forwarded status.

## 2. Body-forbidden matrix

| Final case | Content permitted? | `Content-Length` at upstream | `Transfer-Encoding` at upstream | Trailers/content bytes | Downstream body |
| --- | --- | --- | --- | --- | --- |
| Response to HEAD, if encountered | No | May describe the corresponding GET representation; nonzero is not itself content. Gateway cannot verify hypothetical length and does not claim to. | May describe coding of hypothetical GET under HTTP/1.1; never forwarded by M4-R3. | No response message body/trailer; reliably surfaced bytes are malformed. | None; public HEAD remains unsupported. |
| `204 No Content` | No | Prohibited, including zero. | Prohibited. | No content or trailers; reliably surfaced bytes are malformed. | None. |
| `205 Reset Content` | No generated content | A valid zero-length delimiter may be used; positive declared content is contradictory. | A valid zero-length transfer-coded message may be used where protocol permits; M4-R3 strips framing. | Only an empty terminated message is valid; surfaced nonempty entity bytes are malformed. | None. |
| `304 Not Modified` | No | May describe the hypothetical `200` representation; nonzero is not itself content. Gateway cannot verify hypothetical length and does not claim to. | May describe coding of hypothetical `200` under HTTP/1.1; never forwarded by M4-R3. | No response message body/trailer; reliably surfaced bytes are malformed. | None. |
| `100..199` except `101` | No final content | Prohibited as final-response framing. | Prohibited. | Not a final M4 response. | Not separately forwarded. |
| `101` or CONNECT tunnel | Outside V1 | No M4 final-response transformation or tunnel framing is defined. | Not forwarded as a tunnel. | Unsupported. | No upgrade/tunnel delivery. |

M4-R3's **fixed response allowlist does not include `Content-Length`**, so even legal HEAD/304 representation-length metadata is stripped downstream. Its legality still matters for deciding whether the upstream response is malformed; stripping a legal header does not turn it into a protocol fault. Duplicate/conflicting/invalid framing and malformed header syntax are rejected under M4-R3 and verified protocol-failure rules, not silently normalized. A prohibited 204 `Content-Length` or `Transfer-Encoding`, a positive 205 declared content length, or contradictory framing is a verified upstream protocol failure when reliably observed. Do not infer that all 205 framing rules are identical to 204. Upstream `Connection`, nominated hop-by-hop fields, `Keep-Alive`, `Trailer`, `Transfer-Encoding`, `Upgrade`, `Proxy-*`, and `Set-Cookie` remain filtered per M4-R3; legal `Location` remains forwarded unchanged. The ASGI server, not the upstream, chooses downstream transport framing. No downstream chunked body or fabricated entity bytes are emitted for a valid body-forbidden response; an empty terminal ASGI body message is an implementation detail.

## 3. Observable completion and circuit outcome

For HEAD (if encountered), 204, and 304, HTTP/1.1 declares the message complete at the end of the validated final header section. A correctly parsed final status and validated headers at that **safe parser boundary** establish a complete upstream outcome without waiting indefinitely for an EOF or a body byte. They may then be classified once by M4-R2's final-status table: valid 204/304 are `SUCCESS`; a valid conditional HEAD response would use its final status. This does not certify that future bytes on a persistent connection are harmless. If parser/transport state cannot establish a trustworthy boundary, the Gateway must close/non-reuse the affected connection rather than assert reuse safety. A mere high-level iterator yielding zero bytes is not proof of wire correctness.

For 205, the final response is definitive only when its permitted zero-length framing/termination is verified. A status line and headers alone do not establish that a content-capable 205 message actually ended empty. Await its safe terminal boundary under M4-R10 read-idle behavior; do not wait for a second response or an unbounded absence-of-bytes proof. A verified empty 205 is `SUCCESS`. A response whose upstream framing requires connection close completes when that close establishes the empty message. An upstream timeout or disconnect before a required completion boundary follows M4-R2's corresponding transport result, not a fabricated successful 205.

Reliable evidence of forbidden entity bytes, malformed framing, invalid final status, or parser-reported upstream protocol error **before a definitive outcome is recorded** is M4-R2 `FAILURE` and calls its one provenance-aware failure completion. Never forward forbidden bytes. Do not silently convert a verified malformed response into a successful empty one. Do not treat legal nonzero HEAD/304 metadata length as such evidence. A library may hide bytes following a 204/304/HEAD header section because HTTP/1.1 treats them as bytes for a subsequent message; M4 cannot claim it detected a violation it did not observe. Such ambiguous unread data must never be returned as a known-safe pooled connection. If contamination or a protocol error is discovered only **after** a valid complete outcome has won M4-R9's terminal gate, do not retroactively issue a second circuit completion; close the connection and record only a bounded diagnostic. If a verified upstream transport/protocol failure wins the gate first, its M4-R2 `FAILURE` takes precedence. Gateway-local parsing/coding defects remain `NO_COMPLETION`, not upstream health evidence.

## 4. Downstream commitment, errors, and cleanup

For a body-forbidden final response, the Gateway may commit downstream `http.response.start` after final status, M4-R3-filtered headers, and the applicable safe parser/completion checks above succeed. That event—not upstream header arrival or an empty iterator—ends M4-R10's pre-response deadline. For 205 this requires verified empty completion; for HEAD/204/304 it requires the safe validated header boundary. Before commitment, a verified malformed upstream response maps to the existing safe **503 `upstream_unavailable`** envelope (and M4-R2 protocol `FAILURE`), with no raw framing or upstream detail. A timeout instead retains M4-R10's existing pre-commit **504 `upstream_timeout`** mapping and its M4-R2 classification. This contract introduces no new public error vocabulary.

After downstream commitment, a later upstream protocol/transport failure or unsafe connection state produces **no second status/error envelope**. Stop delivery/terminate the affected response where necessary, close the unsafe upstream response/connection, and apply the first-recorded M4-R9 circuit decision exactly once. A downstream disconnect, shutdown, or definitive concurrency ownership loss cancels/closes only request-scoped work, not the M4-R5 shared `AsyncClient`. M4-R8 renewal remains active until request-scoped downstream delivery and terminal cleanup complete; cleanup stops/awaits renewal, closes the response, and makes its one provenance-aware concurrency release attempt. The read-idle clock remains applicable when upstream streaming is actually being read; no new total-response deadline is introduced. Response body content or raw framing is never logged, audited, or emitted in exception metadata.

Safe pooling requires a clean, protocol-confirmed response boundary and no known stray bytes or framing contamination. If the HTTPX/httpcore API cannot expose enough evidence to assert that for a body-forbidden response, close/non-reuse its connection while keeping the shared client alive. M4-R5's pool limits are unchanged. The locked HTTPX 0.28.1 `Response.aiter_raw()` can expose raw encoded body bytes when there is a body; `aiter_bytes()` may decode content. Neither iterator proves that forbidden bytes absent from its output were absent on the wire. Runtime acceptance must use a synthetic wire server and inspect parser/pool behavior, including whether stray bytes are misread as the next response, before allowing reuse. This contract does not mandate a particular httpcore extension.

## 5. Scope and required later acceptance

A valid body-forbidden response contributes **zero response-content bytes**. Unexpected forbidden bytes are a protocol fault, not an ordinary valid response-size stream; this contract does not invent a numeric response-size ceiling or general response-stream policy. M4-R3 still governs representation headers and M4-R9 generic streaming. No database migration, service/route field, runtime setting, OpenAPI change, or M3-R3A required consumer is introduced. The existing `upstream_unavailable` and `upstream_timeout` error vocabulary covers the pre-commit failures described here. Log only bounded status/protocol/outcome categories and canonical request correlation under M3-R13; never log body bytes, raw upstream headers/framing, credentials, URLs, or raw parser exceptions.

Wire-level acceptance must prove: (1) valid HEAD semantics when internally exercised, without adding public HEAD; (2) legal HEAD `Content-Length` metadata is not mistaken for body; (3) reliably surfaced HEAD bytes are rejected; (4) valid 204; (5) 204 with prohibited `Content-Length`; (6) reliably surfaced 204 bytes; (7) valid empty 205; (8) surfaced nonempty 205; (9) valid 304; (10) legal nonzero 304 metadata length; (11) surfaced 304 bytes; (12) illegal transfer framing; (13) verified malformed protocol before downstream commitment yields safe 503; (14) later violation never yields a second envelope; (15) circuit completion occurs at most once under controlled races; (16) unsafe connection is not reused; (17) shared client remains alive; (18) one concurrency release; (19) pre-response/read-idle clocks follow M4-R10 boundaries; (20) no response-body/raw-framing logging; and (21–22) no migration or new M3-R3A consumer. Use an actual synthetic HTTP/1.1 wire server for hidden/stray bytes; mocked `httpx.Response` alone is insufficient.

## 6. Narrow supersession

M4-R16 supplies the body-forbidden final-response rules left open by M4-R3. It does not change M4-R2 classifications, M4-R3's response allowlist, M4-R8/R9 ownership/cancellation, M4-R10 timeouts, M4-R5 client ownership, or the still-separate general response-size and encoded-body streaming decisions.
