# M4-R11 — Normal API Outbound Destination / SSRF Contract

Status: **FROZEN M4 V1 CONTRACT; M4-R12 EGRESS-PROXY RECONCILIATION REQUIRED BEFORE RUNTIME IMPLEMENTATION.** Documentation only: no application code, schema, test, migration, or OpenAPI change is made here.

## 1. Authority and scope

The M4 Normal API Engine Execution Pack V1.1 permits internal/on-prem HTTP(S) upstreams and forbids Normal API destinations reaching the Gateway platform's PostgreSQL, Redis, Control Plane/Admin, or explicitly tagged management listeners, including hostname aliases and resolved IP/port equivalents. [M4-R1](Enterprise_AI_API_Gateway_M4-R1_Normal_API_Routing_Path_Resolution_Contract.md) fixes the base URL's scheme/authority/path boundary and requires destination validation immediately before connect. [M4-R7A](Enterprise_AI_API_Gateway_M4-R7_Normal_API_Protection_Admission_Ordering_Contract.md) places deterministic local preparation before circuit admission. [M4-R3](Enterprise_AI_API_Gateway_M4-R3_Normal_API_Header_Policy_Contract.md) and frozen OpenAPI already require upstream redirects not to be followed and `Location` to pass through unchanged; this contract does not reopen that choice.

Frozen OpenAPI `x-gateway.egress-security`, shared by Normal API and LLM provider targets, additionally records `denyOwnManagementListeners: true`, `denyMetadataIpv4LinkLocal: 169.254.0.0/16`, `knownNonLinkLocalMetadataDeny: [100.100.100.200]`, and `dnsRebindingProtection: true`. These explicit metadata denies take precedence over the general permission for private/internal upstreams. The HLD recommends a metadata/link-local restriction; its recommendation does not authorize inventing further address ranges or an unreviewed tenant-controlled exception to the frozen OpenAPI denies. The M4 pack's later M9 hardening reference does not defer the OpenAPI's current rebinding-protection requirement: M4 must bind validation to the connection it actually makes, while broader egress allowlists may evolve later.

M4-R11 protects the Normal API service backend destination. It does not redefine TLS trust, credential injection, header forwarding, timeouts, retries, or response handling. M4-R5 leaves HTTPX environment-proxy behavior open; Section 6 makes that a separate prerequisite rather than silently choosing it here.

## 2. Deployment-owned protected-listener inventory

The protected inventory is **deployment/runtime operational configuration**, never tenant-owned or editable through service/route Admin APIs. Tenant and service administrators cannot remove, weaken, or override it. It consists of (a) automatically derived platform connection endpoints and (b) an explicit operator-supplied inventory of listener bindings, aliases, and additional management endpoints. The operator is responsible for declaring all management listener surfaces not observable from this process's client connection URLs; successful parsing of one DSN is not evidence that the whole platform topology has been discovered.

The runtime can derive candidate PostgreSQL endpoints from configured runtime, migration, retention, and security-operations DSNs when present, and Redis endpoints from the configured Redis URL. Parse only network authority/port; never include credentials, paths, or query parameters in the inventory or logs. Derivation protects those client-facing endpoints but cannot discover other container interfaces, port mappings, DNS aliases, or other replicas. The repository's local Compose example exposes PostgreSQL at host port 55432/container port 5432 and Redis at 6379; those example numbers are **not** universal deployment inventory. The application currently has no authoritative Admin/Control Plane bind-address setting, and an ASGI process may bind several interfaces behind a proxy. Therefore the deployment MUST explicitly supply its Control Plane/Admin listener names, bindings, ports, and any PostgreSQL/Redis aliases or listener surfaces not represented by the DSNs, plus any other explicitly tagged management listeners.

The explicit inventory is a required deployment configuration surface, conceptually `NORMAL_API_PROTECTED_LISTENERS`: a structured collection of entries with `kind` (`POSTGRES`, `REDIS`, `CONTROL_PLANE`, or `MANAGEMENT`), `host_or_bind`, and an exact integer `port` in `1..65535`. One entry protects **that listener port** on the normalized hostname/address and its validated aliases/interface addresses; it does not protect every port on the host. Multiple entries represent multiple ports. There is no tenant-scoped inventory field, wildcard port, default allow-all entry, or implicit whole-host deny. A stronger entire-host/network deny belongs to a separately approved deployment egress policy, not to this listener inventory. The eventual Settings serialization and deployment manifest must preserve this exact structure and be validated at startup; M4-R11 adds no code or secret-bearing file format.

Malformed or contradictory explicit entries are startup configuration errors. If required listener coverage is absent or cannot be constructed (notably an undeclared Admin/Control Plane listener, an unparseable required DSN, or an unexpandable wildcard binding), the application may keep its Control Plane/health functionality, but **Normal API execution is not ready and fails closed**. It must not silently use an empty inventory or treat an incomplete inventory as permission to connect. A deployment must attest that the configured entries cover all platform listener aliases and interfaces; software cannot infer undeclared external topology from a local DSN alone. A change to deployment inventory requires rebuilding/validating the effective policy before Normal API traffic resumes; no tenant mutation or Pub/Sub event changes it.

## 3. Normalized destination identity and match

The enforcement identity is the **actual network destination `(canonical IP address, integer destination port)`**. Scheme and original hostname are retained for URL/TLS/Host semantics and alias-based early denial, but hostname-string equality alone never proves safety. Normalize DNS names case-insensitively with unambiguous IDNA/trailing-dot treatment; normalize IPv4 and IPv6 literals, bracketed IPv6 authorities, and IPv4-mapped IPv6 so equivalent addresses cannot bypass comparison. A literal IP URL enters the same address/port matching path as a DNS name. Default ports are 80 for HTTP and 443 for HTTPS only when no explicit URL port is present. A protected listener on `10.0.0.5:5432` denies that pair; `10.0.0.5:8443` is not denied solely because the IP matches. The inventory does not create a blanket private, loopback, multicast, or unspecified-address range ban. Invalid/non-connectable URL authorities fail URL validation, not an invented whole-range SSRF policy.

For an explicit listener bound to `0.0.0.0:PORT` or `[::]:PORT`, the wildcard is **not** a remote destination IP and is never compared literally. Expand it to the actual local interface addresses reachable on that port, including applicable loopback and IPv4/IPv6 addresses, plus declared front-end/port-mapped aliases for that listener. A wildcard does not mean all global IP addresses are protected. If complete relevant interface expansion cannot be established, Normal API fails closed until the deployment supplies concrete listener entries. The effective protected set includes each automatically derived/configured hostname's current resolved addresses at its listener port and each concrete declared binding/alias pair. Preserve the configured host/alias as an early deny input even if its DNS answer later changes; the connection IP/port comparison is still mandatory.

By default, an ordinary RFC1918/private, on-prem, internal-DNS, loopback, or IPv6 local upstream remains eligible if it does not match a protected management listener or the explicit metadata denies. Loopback is not prohibited merely for being loopback. In contrast, **all IPv4 `169.254.0.0/16` destinations and `100.100.100.200` are denied** under frozen shared OpenAPI egress policy, regardless of port or hostname. M4-R11 freezes no additional global cloud-metadata IP list and no broad IPv6 link-local range ban beyond protected-listener matching; a future change requires explicit shared-egress reconciliation. No service-level opt-out applies to the frozen denies.

## 4. Registration, DNS, and validation-to-connect binding

Service `base_url` is Admin-controlled configuration, not client-supplied routing authority. M4-R1 already requires an absolute HTTP(S) URL with a valid authority and no userinfo, query, or fragment; the caller cannot replace its authority. At Admin create/update, reject malformed URL forms and obvious protected literal/declared hostname+port destinations when current inventory proves them forbidden. Admin-time checks are early validation only: persistence or a previous successful check never certifies future runtime network safety. A DNS answer, interface, or deployment inventory may change after registration.

For **every upstream connection attempt**, resolve the configured hostname at runtime immediately before the connection decision, or use an equivalent resolver/connector that validates at selection time. Evaluate **every address the connector could select**, not just the first or the preferred IPv4/IPv6 family. If any candidate is protected at the effective destination port, in the frozen metadata deny set, or cannot be classified reliably, fail closed; do not pass a mixed allowed/protected set to an uncontrolled connector. DNS resolution failure during this security preflight is a local validation failure with no upstream invocation or circuit completion. This does not redefine M4-R2's `FAILURE` classification for a DNS transport failure **after** an admitted real upstream invocation; M4-R2 has no classification action for a pre-admission security rejection. Address ordering and DNS TTL never authorize a previously approved hostname indefinitely; each new connection must revalidate against the current effective inventory. A safe pooled connection may be reused only if its actual peer address/port remains approved under the current inventory for the intended service destination.

**Validation-to-connect invariant:** the address/port approved by this policy MUST be the address/port actually used by the outbound network connection. Resolving and checking a hostname, then passing that hostname to independent HTTPX/httpcore DNS resolution, is insufficient: rebinding between those steps can change the peer. The runtime must pin a validated selected address to the connect operation or provide an equivalent connector-level validated-address guarantee, while preserving the original hostname for HTTP Host and HTTPS certificate-name verification. M4-R11 deliberately does not prescribe a particular transport extension, DNS library, or socket implementation. If the available HTTPX transport cannot provide this guarantee, Normal API implementation remains blocked; it must not claim SSRF protection based on a preflight-only lookup. Existing pooled connections must expose/retain enough trustworthy peer identity to enforce the same rule, or be discarded when that cannot be verified.

## 5. Denial response and M4-R7A ordering

Runtime URL, DNS, metadata, inventory, and protected-listener validation is deterministic **local request preparation before circuit admission** under M4-R7A. On a forbidden destination or failure to establish reliable destination safety, return the existing safe **HTTP 500 `gateway_internal_error`** configuration/security-validation envelope before downstream commitment, without disclosing destination, resolved IPs, management listener identities, or DNS errors. This is a Gateway configuration/safety failure, not client authorization failure, upstream timeout, or evidence of upstream circuit health. The M4 execution pack and static OpenAPI already contain the 500 `gateway_internal_error` family; no new public code is invented. If a downstream disconnect or already committed response makes an envelope impossible, M4-R9 terminal semantics govern instead.

Rate admission may already have consumed tokens and is **not refunded**. A real concurrency handle may already be acquired; the request scope makes its one M4-R7A/M4-R8/M4-R9 provenance-aware terminal release attempt. There is **no circuit admission**, no HALF_OPEN probe claim, no upstream I/O, and no circuit completion for a rejected destination. If an unexpected post-admission transport DNS failure occurs in an admitted real invocation, M4-R2 remains authoritative; local security preflight failure is not reclassified as that transport failure. Redirects remain unfollowed and upstream `Location` remains forwarded unchanged under M4-R3, so a redirect response creates no second destination connection.

## 6. Proxy-path dependency and boundaries

M4-R5 leaves HTTPX `trust_env` and `HTTP_PROXY`/`HTTPS_PROXY`/`ALL_PROXY`/`NO_PROXY` behavior unresolved. M4-R11 does **not** choose whether environment proxies are honored, disabled, or replaced by explicit deployment egress proxy configuration. Its validation-to-connect guarantee must cover the **effective network destination path**. If a proxy is used, the direct TCP peer is the proxy and the ultimate target selection may occur there; merely validating the service hostname in this process is insufficient unless the proxy's trust/enforcement model binds that target and preserves the platform-listener deny rule. An unreviewed environment proxy must not become a bypass.

**M4-R12 — Normal API Egress Proxy / Environment Proxy Contract is a prerequisite before M4 outbound runtime implementation.** It must decide the proxy trust model and how this policy binds to direct or proxied connections. Until then, M4-R11 is a coherent destination-policy contract but not authorization to ship a proxy runtime. TLS certificate verification/custom CA, managed upstream credentials, request/response headers, timeout policy, and redirect rules remain governed by their own contracts; M4-R11 does not change them.

## 7. Schema, observability, and required later evidence

This deployment-owned inventory adds no tenant/service field, database table, migration, Admin API mutation, static/generated OpenAPI field, or M3-R3A required current-state consumer. Existing service/route current-state reconciliation remains a separate M4 requirement; a deployment inventory reload is not a tenant config-version event. Frozen OpenAPI already states the shared egress-security metadata and contains `gateway_internal_error`; no OpenAPI edit is required for this contract. Operational logs may record a bounded denial reason category and canonical request ID, with tenant/service/route correlation only where existing telemetry permits. Never log raw target URLs, DNS answers, listener inventory, credentials, headers, query/body data, or raw exception text; do not make destination/tenant/IP metric labels.

Later acceptance must use controlled resolution/connect fakes and local synthetic listeners to prove: (1) an ordinary private internal upstream is allowed; (2–4) direct PostgreSQL, Redis, and Control Plane/Admin listeners are denied; (5–6) alias and literal-IP equivalents are denied; (7) the same protected IP on an unrelated port is not automatically denied; (8) a mixed protected/allowed DNS answer fails closed; (9) DNS preflight failure fails closed; (10) wildcard bindings expand to applicable local interfaces; (11) changed DNS/inventory after registration is revalidated; (12–15) denial precedes circuit admission, makes zero upstream I/O, releases real concurrency once, and never refunds consumed rate tokens; (16) redirects are not followed; (17) private RFC1918 not matching a protected listener remains allowed; (18) missing/incomplete inventory blocks Normal API execution; (19) IPv4 `169.254.0.0/16` and `100.100.100.200` are denied; and (20) DNS rebinding between validation and connect cannot change the approved peer. Test the chosen M4-R12 direct/proxy path separately before claiming runtime acceptance.

## 8. Narrow supersession

M4-R11 supplies the previously missing deployment inventory and validation-to-connect semantics for M4-R1 and the M4 execution pack. It does not weaken their private/on-prem support or platform-listener deny, does not turn the frozen metadata denies into a generic RFC1918 ban, and does not redefine M4-R3 redirects, M4-R7A ordering, M4-R2 outcome classification for admitted upstream invocations, M3 algorithms, TLS trust, credentials, timeout policy, or future M9 broader egress controls.
