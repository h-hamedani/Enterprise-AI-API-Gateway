# M4-R13 — Normal API TLS Trust / Custom CA Policy Contract

Status: **FROZEN M4 V1 CONTRACT — DOCUMENTATION ONLY.** This contract does not implement a TLS connector or declare the whole M4 engine ready.

## 1. Authority and narrow decision

The [M4 Execution Pack V1.1](../05-implementation/Enterprise_AI_API_Gateway_M4_Normal_API_Engine_Execution_Pack_V1.1.docx) requires TLS verification on and a configured on-prem custom CA path. Frozen [OpenAPI](Enterprise_AI_API_Gateway_OpenAPI_3.1_V1.2_Final.yaml) records `productionTlsVerify: true` and `customCaSupported: true`. [M4-R12](Enterprise_AI_API_Gateway_M4-R12_Normal_API_Egress_Proxy_Policy_Contract.md) requires direct-only Normal API traffic and `trust_env=False`; [M4-R11](Enterprise_AI_API_Gateway_M4-R11_Normal_API_Outbound_Destination_SSRF_Contract.md) requires that a validated address be bound to the actual connection without losing logical hostname identity. [M4-R5](Enterprise_AI_API_Gateway_M4-R5_Upstream_HTTP_Client_Pool_Contract.md) owns the shared client/pool, [M4-R10](Enterprise_AI_API_Gateway_M4-R10_Normal_API_Upstream_Timeout_Policy_Contract.md) owns timeouts, and [M4-R2](Enterprise_AI_API_Gateway_M4-R2_Normal_API_Circuit_Outcome_Classification_Contract.md) owns circuit classification. This document narrows only TLS trust for Normal API V1.

All HTTPS Normal API upstream connections MUST verify the certificate chain and the logical upstream hostname/IP identity. Neither tenant, service, route, nor runtime request may set `verify=False`, disable hostname checks, choose a different trust store, supply an arbitrary CA, or opt out of verification. The default is verification on in every environment, not merely production. The service schema's existing HTTP(S) URL allowance remains: plain HTTP may be used under the already-frozen outbound destination policy, with no TLS handshake or certificate check to perform.

## 2. Trust anchors and explicit deployment CA

For locked HTTPX 0.28.1, `verify=True` with `trust_env=False` constructs the library's **certifi-backed** default SSL context; it does not automatically use the operating system's trust store or read `SSL_CERT_FILE`/`SSL_CERT_DIR`. M4 V1 therefore uses that certifi root set as its default trust anchors. Do not describe this default as system trust. An HTTPX/library upgrade changing this behavior requires compatibility review.

M4 V1 additionally supports one **deployment-owned, startup-only PEM CA bundle path**, conceptually `NORMAL_API_UPSTREAM_CA_BUNDLE_PATH`, applied to the single process-local Normal API client. It is operator configuration, not tenant/service/route persisted data or an Admin API field. A supplied bundle **extends**, rather than replaces, the certifi roots: construct a verifying SSL context from the certifi default and load the configured PEM CA certificates into that same context. Never fall back to `verify=False` or replace the public roots merely because a custom bundle is present. The bundle may contain one or more CA certificates; an empty, malformed, unreadable, nonexistent, or certificate-free configured file is invalid. A configured file that cannot be loaded into the verifying context fails Normal API client startup/readiness, without silent fallback to default-only roots. An absent setting uses the certifi-backed default. The path is explicit; the client does not infer it from ambient certificate environment variables.

The CA bundle contains public trust anchors and is not treated as an upstream credential or private key. Its path/content must not appear in request telemetry, error envelopes, or exception logs. Deployment operators control and protect this trust-policy input. M4 V1 has no per-service CA material, client certificate, private key, or mTLS setting; upstream client authentication and mTLS, if required later, need a separate contract such as M4-R14. This contract does not change managed upstream credential injection.

The trust context is created and validated at application startup with the M4-R5 shared client. Bundle replacement does not hot-reload into an active client or pool; the operator must restart/recreate the process-local client to apply trust-root rotation. No tenant config version, Pub/Sub event, or M3-R3A current-state consumer is involved. Existing pooled TLS connections are not retroactively reverified under a changed bundle; a new process/client and fresh connections are required for a changed trust policy. The exact deployment file distribution and restart orchestration are operational concerns, not new tenant configuration.

## 3. Logical hostname, SNI, and peer binding

The M4-R11 connector may dial a validated literal IP, but HTTPS authority and certificate identity remain those of the configured service `base_url`. For a DNS-name URL, verify the certificate's applicable DNS SAN against that **logical hostname**, and use that hostname for SNI where SNI is applicable; do not silently verify against the selected connection IP or suppress SNI merely because the socket dial uses an IP. For a literal IPv4 or IPv6 URL, verify the certificate using the normal IP-address identity rules, including a matching IP-address SAN. Do not use DNS-name SAN text or disable checks to make an IP literal work. The original URL host also remains the HTTP Host identity under the separate forwarding contract. No implementation mechanism is prescribed here: if the chosen transport cannot preserve logical TLS identity while binding the validated peer IP/port, M4 outbound runtime remains blocked until one can.

The M4-R5 pool may reuse an HTTPS connection only for a compatible scheme, logical authority/hostname, port, TLS trust context, and M4-R11-approved actual peer identity. Do not coalesce or reuse a socket validated for one authority, trust context, or peer as proof of another's safety. M4-R11's current-inventory/peer checks still apply on reuse; an opaque pooled connection with unverifiable peer identity cannot bypass them. Client recreation on trust rotation closes the old pool under M4-R5 ownership. These are safety invariants, not a choice of HTTPX/httpcore extension or a new pool limit.

## 4. TLS failures, public error, and circuit behavior

An invalid **local deployment CA setting** is a startup/readiness configuration failure, before an upstream attempt. It is not evidence of upstream health and has no circuit admission or completion. A runtime remote TLS handshake or certificate-verification failure (untrusted issuer, expired certificate, invalid chain, hostname/IP mismatch, or handshake failure) prevents a complete upstream HTTP response. Before downstream commitment, return the existing safe **`503 upstream_unavailable`** Gateway error envelope; do not expose certificate details, trust anchors, upstream hostname, peer IP, or raw exception text. After downstream commitment, M4-R9 terminal delivery semantics apply; do not emit a second envelope. This uses the M4 execution pack's existing 503 vocabulary and frozen OpenAPI's existing `upstream_unavailable` code, not a new public error.

**Circuit outcome is `NO_COMPLETION` for all TLS handshake and certificate-validation failures**, exactly as M4-R2's normative outcome matrix states. Make no M3 success/failure completion call; a HALF_OPEN owner follows M3's already-frozen probe lifetime. This deliberately differs from the conceptual preference to count remote TLS failure as circuit `FAILURE`: M4-R2 is authoritative, and M4-R13 does not reopen it. A distinct connect/read/write timeout remains classified under M4-R2/M4-R10 according to the actual winning timeout outcome; do not relabel it as TLS failure merely because it occurred during setup. Local CA configuration failure does not reach the classifier at all. Concurrency and cancellation cleanup remain governed by M4-R8/M4-R9.

## 5. Compatibility and required acceptance

The explicit CA setting is deployment-only. No database migration, service/route schema field, Admin API operation, static/generated OpenAPI change, tenant config version, or M3-R3A required consumer is introduced. The frozen OpenAPI already records TLS verification/custom CA support and the existing Gateway error vocabulary. M4-R12 remains authoritative: `SSL_CERT_FILE` and `SSL_CERT_DIR` cannot silently change this client's roots; enabling the custom bundle must not turn `trust_env` back on or enable environment proxy discovery. M4-R11 destination denial still occurs before circuit admission; this contract does not weaken its peer-binding rule.

Later acceptance must prove: (1) a valid public-CA HTTPS upstream succeeds with default trust; (2) a private-CA upstream fails without the deployment bundle; (3) the same upstream succeeds with the configured CA; (4) added CA roots do not remove default certifi roots; (5) custom CA does not disable chain/hostname checks; (6–8) expired, mismatched, and untrusted/invalid-chain certificates fail; (9) literal IPv4/IPv6 URLs require matching IP SANs; (10) HTTP upstreams remain eligible under M4-R11; (11–12) `SSL_CERT_FILE` and `SSL_CERT_DIR` do not affect Normal API trust; (13–14) malformed/empty and unreadable/missing bundles fail startup/readiness without fallback; (15–16) tenants/services cannot disable verification or supply arbitrary CA material; (17) pool reuse cannot cross incompatible logical authority, trust context, or approved peer; (18) SNI and verification retain the logical DNS hostname while connecting to a validated IP; (19) runtime TLS failure yields safe `503 upstream_unavailable` and M4-R2 `NO_COMPLETION`; (20) local CA startup failure yields no upstream circuit event; (21) rotation requires client/process recreation; and (22) no migration or M3-R3A consumer exists. Use controlled local HTTPS fixtures and certificates, not internet endpoints. A preflight DNS mock alone does not prove M4-R11 peer binding.

## 6. Narrow supersession

M4-R13 fills the TLS trust/custom-CA choice left open by M4-R12 and the M4 execution pack. It does not change M4-R2's neutral TLS circuit outcome, M4-R11's destination policy, M4-R5's client/pool ownership, M4-R10's timeout policy, M4-R12's direct-only/environment isolation, or any M3 protection algorithm. Implementation still requires a connector that can simultaneously enforce M4-R11 peer binding and the logical-host TLS verification defined here.
