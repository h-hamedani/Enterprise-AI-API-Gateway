# M4-R14 — Normal API Query String Forwarding Contract

Status: **FROZEN M4 V1 CONTRACT — DOCUMENTATION ONLY.** This document defines query handling; it neither implements the Normal API proxy nor changes the frozen M4-R1 path rules.

## 1. Authority and byte boundary

[M4-R1](Enterprise_AI_API_Gateway_M4-R1_Normal_API_Routing_Path_Resolution_Contract.md) requires the original encoded query sequence, duplicate keys, and ordering to be forwarded separately from route matching/path joining. The M4 Execution Pack V1.1 forbids a plain-dictionary round trip that loses repeated keys. M4-R3 governs headers, M4-R7A governs local-preparation ordering, and M4-R11 governs the configured destination. No existing Normal API runtime forwards a query yet.

The authoritative inbound representation is the ASGI server's raw `scope["query_string"]` bytes. M4 V1 treats those bytes as an **opaque encoded query**: do not UTF-8 decode, parse into a key/value mapping, sort, collapse repeated keys, normalize blank values, interpret `+` as a space, convert `+` and `%20`, change percent-hex case, or decode/re-encode percent escapes merely to forward. Framework `query_params` and a dictionary are not substitutes for the raw ASGI bytes. No M4 V1 Gateway-owned query key is defined; forward the entire accepted sequence without stripping or adding parameters. Query content is never a routing template or an authority/destination input.

**Exact byte preservation is mandatory for accepted queries.** `a=1&a=2`, `a=2&a=1`, `a=&a`, `a`, and `a=` are distinct sequences. Separator placement and spelling remain intact. A percent-encoded non-UTF-8 octet such as `%FF` is just three ASCII query bytes and is forwarded unchanged; the Gateway does not require the percent-decoded value to be valid UTF-8. Valid `%XX` escapes keep their original upper/lowercase spelling. If the inbound stack supplies a malformed escape such as `%`, `%A`, or `%GG` and the outbound connector can send those literal ASCII bytes without mutation, M4 V1 forwards them unchanged: it does not repair them or impose application-level percent-decoding validity. Any downstream interpretation is the upstream's responsibility.

## 2. Accepted wire form and local rejection

The accepted query must satisfy the explicit M4-R14 raw-byte rules below and must be exactly transmittable by the selected outbound connector without mutation. M4-R14 does not require application-level URI percent-decoding validity: a literal `%` is permitted even when it does not form a valid `%XX` escape, provided the connector can transmit the original ASCII bytes unchanged. ASCII URI query characters (including unreserved characters, sub-delimiters, `/`, `?`, `:`, `@`, and literal percent signs) are eligible; percent escapes are not decoded here. Raw non-ASCII octets, spaces, control bytes, and a literal `#` are not forwarded as a query: the latter is URI fragment syntax, not an HTTP query character. Use percent encoding if such data is intended as query data. A percent-encoded `%23` remains eligible and unchanged. An incoming request-target fragment has no separate M4 forwarding semantics. This rule is about wire representation, not requiring the *decoded* query to be UTF-8.

An invalid client-supplied raw query byte sequence receives the existing safe **400 `invalid_request`** envelope before upstream I/O. A query that is otherwise accepted by this contract but cannot be represented **exactly** by the selected outbound URL/connector is a Gateway implementation/configuration limitation, not a malformed client request: fail locally with existing safe **500 `gateway_internal_error`** before upstream I/O. Never silently normalize it, substitute another query, or send a partially changed request. The existing static OpenAPI vocabulary includes both codes; this contract adds no public error code. The error envelope and logs must not echo raw query bytes, parameter names/values, backend authority, or a library exception.

The locked HTTPX 0.28.1 `URL.copy_with(raw_path=...)` can retain an ASCII raw path-plus-query sequence for tested cases such as duplicate keys, `%2f` versus `%2F`, `%FF`, and literal malformed `%GG`; its normal parsed query-parameter APIs are not an acceptable preservation mechanism. It rejects some raw URL components (for example non-ASCII bytes and a literal `#` in the query component). This observation is not a promise that every possible request target is transmitted unchanged by the complete HTTPX/httpcore stack. Runtime implementation must use an API/connector that preserves the accepted raw sequence through the actual outbound request target and test that wire behavior. If it cannot, apply the local 500 rule rather than weakening the contract. No particular lower-level connector extension is frozen here.

## 3. Path composition and the empty-query boundary

First produce the M4-R1 validated upstream scheme/authority/path independently of the query. Then attach the raw accepted query bytes **as the query component**, conceptually `validated_upstream_path + b"?" + raw_query` when `raw_query` is nonempty. Use component-aware construction; never let query text be reparsed as a replacement scheme, authority, port, path, or fragment. A query value containing `http://...`, `//host`, `/`, `?`, or `%23` remains query data. The service base URL itself has no query or fragment under M4-R1. M4-R11 validates the configured network destination, not URLs that merely occur as query text.

The ordinary ASGI `query_string` bytes alone cannot distinguish an inbound request target with no `?` from one ending in an explicit empty `?`: both expose zero-length query bytes. M4 V1 does **not** fabricate that missing distinction. For zero-length `query_string`, the outbound request target omits the query delimiter. If a future server adapter preserves a separately trustworthy empty-delimiter bit and this difference becomes a requirement, that requires a separate contract; it is not inferred from an empty byte string. This is the sole source-level distinction not promised by the M4 V1 byte-preservation guarantee.

## 4. Ordering, safety, and compatibility

Query validation and exact outbound request-target construction are deterministic local preparation under M4-R7A: after rate admission, concurrency acquisition, and the bounded body guard, but **before circuit admission and upstream I/O**. On either local 400 or 500 query rejection, an acquired concurrency handle receives exactly one provenance-aware release attempt, consumed rate tokens are not refunded, and there is no circuit admission, circuit completion, or upstream I/O. This also prevents a query construction error from claiming a HALF_OPEN probe. M4-R9 cancellation precedence still applies if a different terminal decision wins first.

Exact query preservation can be security-relevant to upstream signatures and duplicate-parameter interpretation. It is not an upstream signing feature. No raw query, full request target, parameter value, token, or uncontrolled exception text is authorized for operational logs, telemetry, audit metadata, or error envelopes; bounded decision categories and canonical request correlation remain subject to M3-R13. This document introduces no new Gateway query/request-target size limit or setting. Existing reverse-proxy/ASGI/server parser bounds still apply and must not be bypassed; their specific numeric limits are not frozen here. The M4-R6 request-body limit is not a query limit.

There is no database migration, service or route field, tenant setting, M3-R3A required current-state consumer, or static/generated OpenAPI change. The existing 400 `invalid_request` and 500 `gateway_internal_error` vocabulary covers the two local rejection classes. M4-R1's path validation, M4-R3 header policy, M4-R11 peer binding, and M4-R12/R13 transport security are unchanged.

## 5. Required later acceptance evidence

Prove actual outbound request-target bytes, not merely a parsed HTTPX URL object: (1) `a=1&a=2`; (2) reversed duplicate order `a=2&a=1`; (3) `a=&a`; (4) `a`; (5) `a=`; (6) `%20`; (7) `+`; (8–9) `%2f` and `%2F` retain their differing spelling; (10) `%FF` is not UTF-8-decoded; (11–12) literal malformed `%` and incomplete `%A` are forwarded unchanged when the connector can send them; (13) absent query yields no `?`; (14) an explicit empty `?` is not claimed distinguishable from ordinary ASGI `query_string` alone; (15) reserved characters in accepted query form retain their bytes; (16) `http://...` query text does not change destination; (17) literal `#` rejects as 400 while `%23` remains query data; (18) no query changes authority/path; (19) duplicate-key order survives; (20) no plain-dictionary reconstruction occurs; (21) a valid but unrepresentable sequence produces local 500 rather than normalization; (22–25) local rejection occurs before circuit admission and upstream I/O, releases acquired concurrency once, and does not refund rate; (26–27) no migration or M3-R3A consumer exists. Also test raw non-ASCII/control bytes as 400 where an inbound ASGI fixture can present them, and check that errors/logs do not echo query bytes.

## 6. Narrow supersession

M4-R14 narrows only M4-R1's qualified query-preservation sentence into an exact guarantee for ASGI-supplied raw query bytes that meet this contract's wire-form rule, plus explicit local failure behavior. It does not reopen M4-R1 path normalization, add Gateway-owned query parameters, enable fragments, change routing/destination policy, or choose an HTTPX connector implementation.
