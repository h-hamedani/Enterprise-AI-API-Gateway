# M4-R9 — Normal API Cancellation and In-Flight Abort Contract

Status: **FROZEN M4 V1 CONTRACT; M4-R8 RENEWAL CADENCE REMAINS SEPARATE.** This is contract reconciliation only. It adds no runtime implementation, tests, OpenAPI operation, database migration, or M3 algorithm.

## 1. Authority and boundary

[M3-R3](Enterprise_AI_API_Gateway_M3-R3_Leased_Concurrency_Semaphore_Contract_Reconciliation.md) defines atomic renewable leases: an expired or otherwise missing lease cannot renew, and release of missing ownership safely returns `released=false`. [M3-R10](Enterprise_AI_API_Gateway_M3-R10_Protection_Handle_Provenance_Contract.md) routes renewal and release only to the issuing Redis backend or issuing local generation; a Redis dependency error does not create local ownership. [M3-R11](Enterprise_AI_API_Gateway_M3-R11_Unknown_Circuit_Completion_Result_Contract.md) and [M3-R12](Enterprise_AI_API_Gateway_M3-R12_Local_Circuit_Completion_Lifetime_Contract.md) preserve circuit completion provenance and lifetime. [M4-R2](Enterprise_AI_API_Gateway_M4-R2_Normal_API_Circuit_Outcome_Classification_Contract.md) alone classifies definitive upstream outcomes. [M4-R5](Enterprise_AI_API_Gateway_M4-R5_Upstream_HTTP_Client_Pool_Contract.md) owns one shared `httpx.AsyncClient` per application lifespan/process. [M4-R7A](Enterprise_AI_API_Gateway_M4-R7_Normal_API_Protection_Admission_Ordering_Contract.md) owns admission order and the real concurrency handle's one terminal release attempt.

The M4 Normal API Engine Execution Pack V1.1 requires bounded downstream response streaming, no arbitrary full-response buffering, prompt upstream cancellation on client disconnect, and stream termination rather than a second Gateway error after downstream response commitment. Therefore M4 V1 **does stream generic responses**; this contract does not introduce M6 LLM/SSE semantics. The currently installed HTTPX/httpcore stack handles cancellation as a `BaseException` in request/pool and response-stream paths, removes cancelled pool requests, and closes affected response streams. M4 still has to arrange request-scoped task cancellation and explicitly close any acquired streaming response; it must not assume cancellation undoes upstream processing or close the shared client. Later integration tests must prove these observable properties with the pinned dependency versions.

M4-R9 defines only local request-scoped cancellation, in-flight upstream abort, terminal race/cleanup, and client-visible ownership-loss outcome. It does not set renewal cadence, timeout durations, retry/fallback, SSRF, TLS, or M3 primitive behavior.

## 2. Causes and authoritative ownership

The single Normal API request-execution scope owns upstream work, any acquired circuit completion handle, any real concurrency handle, the future M4-R8 renewal worker, downstream delivery, and one terminal-decision coordinator. Cancellation causes in scope are: definitive concurrency ownership loss; downstream disconnect; application/request-task cancellation during local termination or shutdown; and an internal local decision/fault that ends execution before a definitive upstream result. Cancellation is request-scoped. It cannot close/recreate the shared `AsyncClient`, cancel unrelated requests, or create a new upstream attempt.

`renewed=false` for the exact issued handle is **definitive loss for this request**, whether caused by expiry, missing/stale ownership, invalid provenance, or a missing issuing local generation. A known local handle may similarly be known expired under M3's own lifetime semantics. A typed Redis/dependency exception is **unknown renewal result**, not proof of lost ownership: M3-R10 forbids changing a Redis-issued handle into a local lease. M4-R8 must separately define bounded uncertainty handling and whether/when a subsequent result establishes loss; M4-R9 does not equate one transient failure with `renewed=false` or permit indefinite unaccounted execution.

M4 does **not** allow upstream or downstream work to continue after definitive concurrency ownership loss. Once the request scope observes and terminally records that loss, it aborts request-scoped upstream work and downstream delivery. This preserves the meaning of the concurrency limit; it is not an automatic retry or a circuit failure.

## 3. Cancellation by execution phase

Before upstream request creation, terminal cancellation performs no upstream I/O. Before circuit admission, it also makes no circuit admission or completion call, preserving M4-R7A's probe-safe order. After successful circuit admission but before actual upstream I/O, cancellation makes no fabricated circuit success/failure call; an owned HALF_OPEN probe remains governed by its existing M3 probe lease and later eligibility replacement. Request construction should already be complete under M4-R7A, minimizing this window.

During upstream connect, write, read, or response streaming, definitive ownership loss cancels the request-scoped upstream operation promptly, closes any acquired HTTPX response, and stops further downstream delivery. The same prompt abort applies to a disconnect, shutdown/request-task cancellation, or a terminal internal local fault. Cancelling an HTTP request **does not establish that the upstream server did not receive or process it**; non-idempotent side effects may have occurred. M4 V1 does not retry or fall back.

If an error is returned while downstream headers are still writable, definitive ownership loss returns the existing normalized **HTTP 500 `gateway_internal_error`** envelope with the canonical request ID and a safe generic message. Ownership loss is a local protection-accounting failure, not evidence that the configured upstream is unavailable; do not label it `upstream_unavailable`, `rate_limit_exceeded`, or `upstream_timeout`. A disconnected client or externally cancelled/shutting-down request receives **no fabricated HTTP response**. An ordinary internal local exception follows the existing safe Gateway internal-error boundary if response commitment has not occurred. This contract does not choose a new public code.

After downstream headers/body are committed, no second status or JSON envelope can be sent. Stop the downstream body/connection promptly and record a sanitized aborted-delivery result. This includes an ownership loss during a long generic response stream. The shared client and other requests remain usable; the affected HTTPX connection is closed or retained only according to HTTPX's safe pool state, never forced back into service by M4.

## 4. Definitive outcome and race fence

One request-local terminal-decision gate serializes observation of a **definitive upstream outcome** against a terminal local cancellation decision. A final status with the complete upstream response, or a verified M4-R2 upstream transport failure, is definitive only when M4-R2 says so; response headers or partial streamed bytes alone do not manufacture a completed upstream outcome. The first decision recorded at the gate wins. If the upstream outcome is recorded first, complete the circuit at most once from that outcome, even if downstream delivery later aborts. If cancellation/loss is recorded first, cancel/close upstream work and classify `NO_COMPLETION` unless a definitive upstream outcome had already been recorded. An outcome that arrives after cancellation has won cannot retroactively alter circuit state or cause a second client response. A locally produced cancellation exception is not reclassified as connect/read/write failure.

For concurrent ownership loss, disconnect, shutdown cancellation, and upstream completion, the same first-recorded gate decides circuit outcome and whether a still-writable client can receive a response. A downstream disconnect or shutdown cancellation recorded first means no client response. A definitive ownership-loss decision recorded first means the safe pre-commit 500 if still writable. An upstream outcome recorded first retains its M4-R2 classification; a later disconnect/loss can still abort remaining downstream delivery but cannot rewrite circuit health. Terminalization occurs at most once: no second downstream response, no second circuit completion, no second release attempt, and no renewed upstream work. Tests must control this order with synchronization primitives, not arbitrary sleeps.

## 5. Cleanup and shutdown

All paths converge on the request-execution scope's single cleanup owner. On a terminal decision, request-scoped upstream work is cancelled when still active; any acquired HTTPX streaming response is closed. Stop the future renewal worker and await its termination before the **one** M4-R7A concurrency release attempt, so renewal cannot race a terminal release or run afterward. Circuit completion, if a definitive outcome won, is attempted at most once with the issued provenance-aware handle; cleanup must not fabricate a circuit result if it did not. Cleanup must be cancellation-safe and bounded by the existing request/server shutdown mechanics; no untracked renewal or upstream task may survive the request scope.

For every actual acquired concurrency handle, terminal cleanup attempts release **once even after `renewed=false`**. M3-R3 makes this safe: missing/expired ownership returns `released=false`, and partial caller-owned residue can be removed without touching another lease. Release uses the original M3-R10 provenance and does not try the currently healthy backend as a substitute. No renewal or release is attempted for a denied acquisition or an empty-policy null handle. A failed/false release is recorded safely and never triggers a second release path or replaces an already committed client result. Lease expiry remains the crash-recovery safety net, not normal active-request ownership.

On graceful application shutdown, stop admitting new Normal API execution in that process, allow request-scoped work to finish within the server's configured graceful boundary, and cancel remaining active scopes when that boundary ends. Each ending scope performs the same upstream/renewal/circuit/release cleanup. The shared `AsyncClient` is closed by its M4-R5 lifespan owner only after request-scoped work has been resolved to the extent the server's graceful-shutdown lifecycle permits. No distributed drain, handoff, or new shutdown timeout is defined here. If a disconnect causes execution to end, the same request-scoped cancellation and release obligation applies; M4-R9 does not prescribe how frequently the server polls for disconnects.

## 6. Observability, compatibility, and M4-R8 handoff

Record bounded categories for ownership-loss cancellation, transient renewal dependency error (without calling it definitive loss), client disconnect, shutdown/local cancellation, pre-/post-upstream start, and aborted downstream delivery, correlated with the canonical request ID. Persist tenant/service correlation only where the existing telemetry schema authorizes it; never use their IDs as metric labels. Do not record bodies, headers, credentials, lease/probe IDs, Redis keys, raw URLs or queries, or raw exception text. Do not add metrics infrastructure or a new audit action.

M4-R8 takes these frozen inputs: `renewed=false` is terminal definitive loss; active upstream/delivery is cancelled; pre-commit loss uses safe 500 `gateway_internal_error`; post-commit loss terminates delivery; circuit completion depends only on the race-gated definitive upstream outcome; stop/await renewal before one provenance-aware release attempt. A dependency exception is unknown, not definitive, and M4-R8 must freeze its bounded handling and cadence. This contract changes no M3 algorithm, M4-R7A admission order, M4-R2 outcome set, timeout duration, or M6 retry/fallback behavior.

The existing OpenAPI `ErrorResponse` vocabulary includes `gateway_internal_error`; the M4 pack already lists 500 for gateway internal errors and already requires stream termination after commitment. **No OpenAPI change** is needed. This contract adds no persisted field/table/migration or new M3-R3A current-state consumer: cancellation state and worker ownership are request-local; M3 lease duration remains deployment configuration.

## 7. Required later tests

Unit and integration tests must cover loss before upstream creation; loss after circuit admission but before I/O; loss during connect, write/read, and downstream response streaming; loss racing with complete response; disconnect while upstream work is pending; shutdown/request-task cancellation; internal exception; and local cancellation exception distinct from M4-R2 transport failure. Assert no upstream I/O before creation, no fabricated circuit result, current HALF_OPEN probe left to existing expiry on `NO_COMPLETION`, at-most-once terminalization/completion/release, safe no-op release after ownership loss, and no retry.

With a local synthetic upstream and controlled synchronization, block one upstream attempt after the request acquires concurrency, inject the frozen definitive ownership-loss result, and prove the request-scoped task and upstream response end while the shared client remains open and another concurrent request remains unaffected. Verify the first scope attempts one release and a subsequent request can execute. Separately exercise response headers already committed: abort the body without a second HTTP response. Tests must prove that cancelled/unsafe transport is not reused as healthy unless HTTPX safely returns it to the pool; do not assert undocumented socket internals. No external network is required.

## 8. Narrow supersession

M4-R9 qualifies M4-R7A only for request-scoped cancellation, in-flight abort, client-visible ownership-loss result, terminal-race fencing, and cleanup coordination. It does not redefine M3-R3 acquisition/renewal algorithms or TTL bounds, M3-R10 provenance, M4-R7A admission order/rate/body/circuit behavior, M4-R8 renewal cadence, timeouts, SSRF/TLS, retries, fallback, or M6 streaming semantics.
