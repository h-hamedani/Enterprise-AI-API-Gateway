## 1. Authority and completion boundary

[M4-R6](Enterprise_AI_API_Gateway_M4-R6_Normal_API_Request_Body_Limit_Contract.md) fixes the effective raw-byte limit, immediate valid `Content-Length` overflow rejection, actual ASGI-byte counting, and zero upstream I/O on 413. [M4-R7A](Enterprise_AI_API_Gateway_M4-R7_Normal_API_Protection_Admission_Ordering_Contract.md) requires bounded body preflight and deterministic local preparation before circuit admission. [M4-R3](Enterprise_AI_API_Gateway_M4-R3_Normal_API_Header_Policy_Contract.md) owns header/framing filtering; [M4-R8](Enterprise_AI_API_Gateway_M4-R8_Normal_API_Concurrency_Lease_Renewal_Contract.md), [M4-R9](Enterprise_AI_API_Gateway_M4-R9_Normal_API_Cancellation_and_In_Flight_Abort_Contract.md), and [M4-R10](Enterprise_AI_API_Gateway_M4-R10_Normal_API_Upstream_Timeout_Policy_Contract.md) own renewal, cancellation, and timeout clocks. The frozen OpenAPI vocabulary already includes `invalid_request`, `request_too_large`, and `gateway_internal_error`.

The authoritative entity source is the ASGI inbound receive stream. For each `http.request` message, treat `body` (or its ASGI empty default) as entity bytes and `more_body` (or its ASGI false default) as the continuation indicator. A normal `http.request` with `more_body=False` completes the entity. An empty final request message yields a valid zero-length entity. Merely having received no message does **not** prove completion. `http.disconnect` before normal completion is a confirmed client disconnect, not a zero-length final body. A receive-call exception is classified under Section 4, not silently treated as end-of-body.

**The entire accepted entity MUST be received and validated within the M4-R6 bound before circuit admission, upstream request creation/send, or any upstream body byte.** No inbound-to-upstream streaming while total size or completion is unresolved is permitted in M4 V1. The completed body may be held in bounded memory or a bounded request-scoped spool; M4-R6 explicitly allows either and this contract does not choose a medium. The storage must not grow beyond the effective bound, must preserve the entity bytes exactly, and must be cleaned on normal completion, failure, disconnect, or cancellation. If a spool cannot be read back reliably, do not send a partial body. At the approved upper limit of 64 MiB per request, in-memory storage is permitted but process/concurrency memory safety must be demonstrated by the implementation; no unbounded extra copy or hidden full-body duplicate is authorized by this contract.

## 2. Byte and framing semantics

Forward **exactly the accepted entity-byte sequence**, irrespective of ASGI message boundaries. Do not parse/reserialize JSON, multipart/form-data, URL-encoded forms, protobuf, or other binary formats; do not transcode text, normalize whitespace, or decompress/recompress an encoded entity. Inbound HTTP chunk sizes, chunk boundaries, and transfer coding are transport framing, not entity bytes: they need not and MUST NOT be copied as application semantics. ASGI has already delivered entity bytes abstracted from inbound transfer framing. Do not forward inbound `Transfer-Encoding` or `Trailer` headers or invent application-visible trailer forwarding in M4 V1. No authoritative M4 artifact requires inbound trailer propagation; any future trailer support needs a separate contract.

M4-R3 strips inbound `Content-Length`, `Transfer-Encoding`, and hop-by-hop framing fields before outbound construction. The outbound HTTP client chooses legal framing from the **accepted complete entity length**; for a finite materialized body it may generate `Content-Length` equal to the actual forwarded bytes. It must never reuse an inconsistent inbound length or relay inbound chunk framing. For zero bytes, do not synthesize semantic body content; an outbound zero length/no entity framing permitted by the client is acceptable. GET and DELETE may carry an entity under M4-R6; method name alone neither rejects nor alters it. POST/PUT/PATCH are likewise forwarded according to the actual entity, not a JSON assumption.

`Content-Type` is forwarded only when M4-R3's effective policy allows it for an actual body, unchanged as a header value; M4 does not validate content against its media type. `Content-Encoding` is not in M4-R3's default request allowlist. If explicitly allowed, its header is forwarded only with the unchanged encoded entity bytes; no decompression or framing inconsistency is introduced. A duplicate/invalid singleton or forbidden framing header remains subject to M4-R3's earlier `400 invalid_request` rule. This contract does not expand the header allowlist.

## 3. Declared length, actual count, and precedence

For a syntactically valid, unambiguous inbound `Content-Length: N`, normal completion is length-consistent only if the total ASGI-delivered entity length equals `N`. If normal completion yields fewer than `N`, reject **400 `invalid_request`**. If delivered bytes exceed `N` while still within the effective M4-R6 limit, reject **400 `invalid_request`**; do not relabel the excess as an absent-length body or forward it. The Gateway may detect that excess as soon as it is observable. Terminal classification follows the earliest observable winning condition. If a declared-length excess is observed while the actual byte count remains within the effective M4-R6 limit, that condition terminates locally as 400 invalid_request and later bytes are not consumed merely to discover a possible 413. If the effective body limit is crossed before any earlier terminal decision has been recorded, the winning result is 413 request_too_large. No later mismatch or size signal overwrites an already-recorded terminal decision. A valid declared `N` already above the effective limit yields immediate 413 without consuming the whole body. A missing length is valid: receive through normal `more_body=False`, count actual bytes, accept when within the limit, and derive outbound framing from that completed count. Exactly the limit passes; its next byte triggers 413.

The decision order is: (1) M4-R3 rejects syntactically invalid or ambiguous framing as 400 before trusting any length; (2) valid declared length above the effective limit is immediate 413; (3) while receiving, an observed disconnect takes the M4-R9 cancellation path, and actual count above the limit is 413 when it is the first terminal decision; (4) a length mismatch observed at or before normal completion is 400 if no earlier terminal decision won; (5) an unknown/internal receive failure is the safe 500 boundary in Section 4; (6) otherwise preflight succeeds. This ordering does not assert that a disconnected client can receive a 413 or 400 after transport loss. M4-R9's first-recorded terminal-decision fencing applies to races; no later signal overwrites a decision already made.

## 4. Disconnect and receive failures

If `http.disconnect` is observed before body completion, or the server/framework explicitly defines a raised exception as a client-disconnect/cancellation equivalent, terminate under M4-R9. Do not infer ordinary client malformation merely from missing bytes after a confirmed disconnect, and do not fabricate an HTTP response to a gone transport. Cancel request-scoped work, stop/await renewal, release an acquired concurrency handle through its one provenance-aware attempt, clean any body storage, and make no circuit admission, completion, or upstream I/O.

If `receive()` raises an **unknown/internal** error before normal completion and no authoritative disconnect was observed, treat it as a Gateway receive-path failure: return safe **500 `gateway_internal_error`** if downstream response commitment and transport state still permit a response. Do not call it `400 invalid_request` without evidence of malformed client input, expose the exception, assume an empty tail, or send a partial body upstream. An independently established request cancellation still follows M4-R9. A normally completed stream with a declared-length shortfall is instead the 400 case in Section 3, even if a particular server commonly prevents that state from reaching ASGI.

All body-preflight exits occur before circuit admission and upstream request creation/I/O. Consumed rate tokens are not refunded. If a real concurrency handle was acquired, M4-R8 renewal remains active during body receipt and preparation until terminal cleanup; M4-R8/R9 then stop/await renewal before exactly one provenance-aware release attempt. There is no circuit completion or HALF_OPEN probe claim. Inbound body receipt consumes none of M4-R10's upstream transport or pre-response budget, which starts immediately before the later HTTPX send. No new body-receive deadline is introduced here.

## 5. Compatibility, privacy, and required acceptance

These results use existing Gateway errors: 400 `invalid_request` for invalid framing or length inconsistency, 413 `request_too_large` for the M4-R6 limit, and 500 `gateway_internal_error` for an unknown internal receive failure when a response is still possible. They require no new public error code or static/generated OpenAPI change. Never log or audit body bytes, multipart/JSON values, raw binary content, credentials within a body, or raw receive exceptions. ## 6. Narrow supersession

M4-R15 fills only M4-R6's deferred request-body forwarding and incomplete-body semantics. It does not move the M4-R7A circuit gate, change M4-R3 header policy, alter M4-R8/R9 ownership/cancellation, shift M4-R10 timeout clocks, introduce upstream streaming or body transforms, or choose a spool implementation.
