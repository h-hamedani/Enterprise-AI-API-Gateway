# M4-R17 — Normal API Response Streaming / Downstream Commit Contract

Status: **FROZEN M4 V1 CONTRACT — DOCUMENTATION ONLY.** This contract fixes ordinary content-permitted response streaming and downstream commitment. It does not implement a transport or reopen M4-R16's body-forbidden statuses.

## 1. Authority and byte model

[M4-R3](Enterprise_AI_API_Gateway_M4-R3_Normal_API_Header_Policy_Contract.md) requires filtered response headers and raw entity bytes consistent with `Content-Encoding`. [M4-R9](Enterprise_AI_API_Gateway_M4-R9_Normal_API_Cancellation_and_In_Flight_Abort_Contract.md) requires bounded generic streaming, one request-local terminal gate, and no second error envelope after commitment. [M4-R10](Enterprise_AI_API_Gateway_M4-R10_Normal_API_Upstream_Timeout_Policy_Contract.md) ends the pre-response deadline only at committed downstream `http.response.start`; its read-idle timeout continues during upstream streaming. [M4-R2](Enterprise_AI_API_Gateway_M4-R2_Normal_API_Circuit_Outcome_Classification_Contract.md) requires a complete definitive upstream outcome or verified transport/protocol failure before circuit completion. [M4-R16](Enterprise_AI_API_Gateway_M4-R16_Normal_API_Response_Forwarding_Contract.md) remains authoritative for HEAD, 1xx, 204, 205, 304, and unsupported upgrade/tunnel cases.

Ordinary response content is forwarded as the upstream **encoded representation/entity bytes**, not decoded application content. Use semantics equivalent to locked HTTPX 0.28.1 `Response.aiter_raw()` in streaming mode. Its `aiter_bytes()` may decode gzip, deflate, Brotli, or Zstandard; `aread()` materializes decoded content and is not the transparent bounded-stream path. Do not decompress/recompress, transcode, or parse response content. Preserve allowed `Content-Encoding` with the unchanged encoded bytes, whether its coding is gzip, deflate, br, zstd, or an unknown token. If a coding is not understood by HTTPX, transparent forwarding still does not require decoding it. The implementation must prove raw-byte and header consistency at the actual HTTPX/ASGI boundary.

M4-R3's response allowlist strips upstream `Content-Length` and hop-by-hop `Transfer-Encoding`, `Trailer`, and `Connection` fields. It may retain allowed representation metadata such as `Content-Type`, `Content-Encoding`, `ETag`, or `Location` unchanged under that policy. Downstream framing is selected by the ASGI server for bytes actually delivered; upstream chunk boundaries are not semantic and are not reproduced. An upstream valid `Content-Length` remains useful as **framing-validation input**, not an automatically forwarded downstream header. A short or long body is a verified upstream protocol/transport failure only if the parser/connector can reliably establish the discrepancy; do not claim detection solely from a header or silently reuse a contaminated connection. No full-body buffer is required to validate length before downstream commitment.

## 2. First-byte-or-empty-completion commitment

For an ordinary final status where content is permitted, validated final upstream status and M4-R3-filtered headers **alone do not authorize downstream `http.response.start`**. Commit only after either (a) at least one nonempty raw upstream representation-byte chunk has been successfully obtained and retained for immediate downstream forwarding, or (b) the upstream response has authoritatively completed as a valid zero-content response under its framing without any body byte. A nonzero `Content-Length`, an HTTPX `Response` object, or an empty iterator yield before terminal completion does not substitute for this boundary. M4-R16's separate header-boundary and no-content status rules remain unchanged.

The first nonempty raw chunk is held in a bounded request-scoped buffer; do not decode, alter, discard, or send it before a successful downstream response-start commitment. After commitment, forward those exact bytes as the first body output, then stream later raw chunks incrementally. The exact chunk or bounded queue size is an implementation choice. If the upstream cleanly completes with zero content, commit the validated status/filtered headers and finish downstream with no fabricated byte. There is no requirement to wait for a nonexistent first byte.

M4-R10's separate monotonic pre-response deadline starts immediately before the upstream send and continues through final-header acquisition, filtering, waiting for first raw bytes or valid empty completion, and actual downstream response-start commitment. **Receiving the first chunk alone does not end that deadline**: it ends only when `http.response.start` is successfully committed. If a timeout, ownership loss, disconnect, or other terminal decision wins before commitment, no ordinary upstream response-start is emitted. After commitment the pre-response timer is disarmed; read-idle remains active when awaiting subsequent upstream reads. Slow downstream sends/backpressure do not become artificial upstream read-idle failures when no upstream read is pending. No total response-duration deadline is introduced.

## 3. Streaming, outcome, and failure separation

After commitment, incrementally couple upstream raw reads to downstream sends with **bounded in-flight buffering and backpressure**. Do not materialize an arbitrary full response or permit unbounded read-ahead while downstream is slow. An exact queue/chunk size is not contractual; observable bounded memory and prompt request-scoped cancellation are. This applies to binary downloads, long polling, and HTTP/SSE-shaped long-lived responses as ordinary bytes; it introduces no M6 LLM/SSE event semantics or WebSocket protocol. The execution pack expressly has **no small fixed response-size ceiling in M4 V1**. M4-R17 adds no total-response byte cap or size setting; resource safety comes from bounded in-flight buffering, the existing timeouts, renewal, and cancellation, not full-body materialization.

Downstream commitment, first byte, and partial delivery are **not circuit completion**. A content-permitted final upstream response becomes definitive only when its framing reaches a clean terminal boundary, all upstream entity bytes have been consumed successfully, and no earlier M4-R9 terminal cancellation or M4-R2 transport/protocol failure won. Classify that complete response by M4-R2's final status once: e.g., a complete `200` is circuit `SUCCESS`; a complete selected `500` is `FAILURE`. A verified upstream reset, truncation, malformed framing, or read-idle timeout **before clean completion** instead yields the applicable M4-R2 transport/protocol `FAILURE` once; an upstream `500` whose body truncates produces one failure decision, not a status completion plus another failure. A local cancellation/deadline before a definitive upstream outcome is `NO_COMPLETION` where M4-R2/R10 require it. The first recorded M4-R9 terminal decision wins; do not retroactively classify after a cancellation won.

The upstream entity may be fully consumed and the circuit result recorded while downstream delivery remains queued behind bounded backpressure. A later downstream delivery failure does not rewrite that definitive upstream result. **Concurrency lifetime is different**: M4-R8 renewal continues through downstream delivery and terminal cleanup, even after upstream circuit completion; do not release the handle merely because the upstream has completed. Terminal cleanup stops/awaits renewal and makes one provenance-aware release attempt under M4-R9.

Before downstream commitment, a verified upstream connect/reset/read/protocol failure maps to the existing safe **503 `upstream_unavailable`** envelope where no more specific frozen timeout mapping applies. A connect/write/read/pool timeout or the separate pre-response deadline maps
to M4-R10's 504 upstream_timeout. Circuit classification remains distinct:
an independently observed HTTPX connect, write, or read/read-idle timeout is
M4-R2 FAILURE, while a pool timeout and the separate Gateway pre-response
deadline are NO_COMPLETION. These client-visible mappings do not change the
frozen circuit semantics. An internal Gateway fault remains under the existing safe 500 boundary. After commitment, a stream failure, read-idle timeout, disconnect, or definitive ownership loss produces **no second response/error envelope**: terminate affected downstream delivery, classify only a definitive M4-R2 outcome that won the gate, and perform request-scoped cleanup. The shared `AsyncClient` survives.

If a downstream disconnect or ownership-loss cancellation interrupts an incomplete upstream stream, promptly cancel/close that response and stop further reads; do not fabricate a completed HTTP result. A completed, cleanly framed response may return its connection to the M4-R5 pool only if the transport establishes safe reuse. A truncated, cancelled, abandoned, protocol-invalid, or uncertain-unread response must be closed or otherwise made non-reusable unless the transport proves safe draining/reuse. Never close the shared client as per-request cleanup. The read-idle limit measures an awaited upstream read operation; received upstream progress resets the next read wait, while downstream backpressure alone is not an upstream read timeout.

## 4. Privacy, compatibility, and required acceptance

Do not log/audit response-body or encoded bytes, raw framing, raw response headers, credentials within content, or uncontrolled protocol exception text. Existing bounded status, byte-count, latency, and outcome categories are permitted only within M3-R13 and current telemetry governance. No database migration, service/route field, runtime setting, static/generated OpenAPI change, or M3-R3A required consumer is introduced. The existing `upstream_unavailable`, `upstream_timeout`, and `gateway_internal_error` vocabulary covers the pre-commit boundaries; M4-R3, M4-R5, M4-R8/R9/R10, and M4-R16 are not superseded outside this narrow commitment/streaming decision.

Later acceptance must prove: (1) headers plus immediate first chunk; (2) delayed first chunk remains under the pre-response budget; (3) valid zero-length ordinary response; (4–5) reset/protocol failure after headers but before first byte; (6) read timeout before first byte; (7) pre-response deadline before first byte; (8) first chunk available but response-start not yet committed does not stop the deadline; (9) retained first chunk is forwarded exactly; (10–12) binary and gzip/other encoded bytes match forwarded `Content-Encoding`; (13) a long multi-chunk stream; (14–15) bounded downstream backpressure without full buffering; (16) upstream mid-body disconnect; (17) downstream mid-body disconnect; (18) mid-body read-idle timeout; (19) mid-body ownership loss; (20–21) no circuit result from headers or first byte; (22) exactly one definitive upstream completion/failure; (23) downstream completion can follow circuit completion; (24) renewal continues through downstream delivery; (25–26) unsafe connection non-reuse and safe completed reuse; (27) no second envelope after commitment; (28) shared client survives request failures; (29) no body logging; and (30) no migration or M3-R3A consumer. Include synthetic wire-level fixtures for short/long `Content-Length`, chunked framing, delayed bytes, and protocol errors; control races with synchronization, not arbitrary sleeps as correctness proof.

## 5. Narrow supersession

M4-R17 fills only the ordinary content-permitted response-start and streaming boundary left open after M4-R16. It does not alter body-forbidden status completion, M4-R2 outcome classes, M4-R3 header policy, M4-R10 timeout values, M4-R9 first-terminal decision, or M4-R5 shared-client ownership.
